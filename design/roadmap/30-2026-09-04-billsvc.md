# 2026-09-04 — the billing plane

Phase 8's third and fourth items (`design/19-server-platform.md` §4/§5, ROADMAP 8.3/8.4): a third
process with its own SQLite file, the five idempotency-and-trust rules that make taking money
safe, one IAP adapter per platform behind one factory, and the dev receipt stub that makes the
whole chain drivable with no merchant account in existence.

## The billing plane (2026-09-04, server only, no engine bump)

**The shape.** Third process on 8789, beside the data plane (8787) and the control plane (8788),
with its own database file behind its own `BB_BILLING_DB_PATH` and its own opener — never
`db.ts`'s `openDb`, because "money gets its own database file" is a locked decision and a shared
opener is exactly how a later refactor quietly re-merges them. Three tables and no more: `orders`,
`receipts`, and a `ledger` that is only ever appended to. 15 source files, every one well under the
500-line convention, plus 7 test files carrying 213 cases — the server package went 462 → 675
tests, its coverage reads 99.46% lines / 96.93% branches, and `src/billsvc/` itself measures
99.51% statements / 98.79% branches / 100% functions / 99.45% lines.

**The five rules, and the one the plan did not have.** design/19 §4 names five, each written by a
failure funny actually hit, and four went in as specified: price read from a server-side SKU table
(`createOrder` has no `amount` **parameter** — not "ignores one", so a pass-through cannot be
introduced by mistake); delivery reachable only from the platform callback, never from the client,
whose `POST /order/create` gets payment parameters and whose `GET /order/:id` can only poll; a
receipt row that records the product it **resolved to**, without which a receipt bought for one SKU
is replayable against another; and another account's consumed receipt **refused rather than
replayed**, funny's own comment being the whole argument (a replay mirrors the owning account's
state back to whoever posted the callback).

The fifth needed a second half the plan did not anticipate. §4 names `platform_txn_id`'s UNIQUE
constraint as *the* idempotency key, claimed with `INSERT ... ON CONFLICT DO NOTHING` and read
through `changes()`, never SELECT-then-INSERT. That is correct and it is not sufficient: `txnId`
arrives in the **callback body**, which nothing authenticates, so one dev-stub receipt posted at
three different orders with three invented transaction ids wins three claims and delivers three
times. So `settle` claims **twice** — the receipt row's primary key first, then the ledger row's
`purchase:<platform>:<txn>` id — and prefers `verified.platformTxnId` over the body's whenever an
adapter supplies one, because the receipt is verified and the body is not. Losing the first claim
is a redelivery; losing the second after winning the first means one transaction presented under
two receipts, which is refused rather than resolved silently in either direction.

**Rule 4 moved inside the transaction, and that is the interesting part.** It first shipped as a
`SELECT account_id FROM receipts` before `BEGIN IMMEDIATE`. That is correct today and correct for a
reason that is not in the design: there happens to be no `await` between the read and the claim.
Written that way, the guarantee is a property of the current code rather than of the lock, so the
ownership question is now answered from the **lost claim**, under the write lock the transaction
already holds — and the refusal deliberately says nothing about the owner.

**funny's verify-and-heal saga stayed out, and now there is a test that says why.** Its CAS claim
fields (`healedAt`, `healClaimedAt`) exist because its receipt row and its wallet increment are
separate Mongo documents with no transaction around them: a crash between the two loses the
purchase, and two concurrent healers both observing "no ledger entry" both re-grant. Here the order
update, the ledger row and the entitlement grant are one `BEGIN IMMEDIATE`, so the tear is
impossible and the machinery would be complexity with no failure behind it. What makes that claim
load-bearing rather than decorative is `delivery.ts`'s seam: the grant is called **from inside** the
transaction, and three cases assert what follows — a throwing grant rolls order, receipt and ledger
back together, the platform's next retry then succeeds because the order is still open, and the
connection stays usable afterwards. If the order row survived a failed grant, that saga would be
necessary here after all and design/19's decision would be wrong.

**Fail closed twice, and the two checks share no code on purpose.** `iap/factory.ts` consults
`NODE_ENV` **before** it reads `BB_BILLING_DEV_STUB`, so a mis-set flag on a production box is
inert rather than catastrophic, and a platform with no credentials returns a failure rather than
falling back to the stub — missing credentials mean verification fails and nothing is granted, in
any environment. `startupGuard.ts` then refuses to let the process **start** at all with a dev flag
set in production, before a port is bound or a database file is created. The obvious tidy-up is for
the guard to import `devStubEnabled` from the factory; that would make both defences one defence
with two call sites, and a bug in that predicate would take out both at once. The three-line
predicate is duplicated deliberately and each has its own test asserting its own copy — design/19's
"one of those checks is the design; two is the design surviving a deploy", made structural.

**The dev stub is the reason any of this could be tested at all.** No Apple, Google, WeChat or
Stripe credential exists anywhere in this project (§9), so the four real adapters ship as shape
only: two outcomes each, both failures, neither throwing — a missing credential and a round trip
that is not implemented. Every one carries the real call it would make (Apple's production-first-
then-sandbox retry order, which the other way round accepts sandbox receipts in production;
Google's `product` that must come from the API response and never from the client-supplied
envelope; WeChat having no receipt at all, so the SKU comes from the merchant's own order row).
A `product:<sku>` receipt resolves locally on **any** platform while the stub is on, which is what
lets `/webhook/apple` be driven end to end, and the whole chain — create → "pay" → callback →
delivered → redelivery reports `delivered: false` — was run against the real process, not only in
tests. The SKU table sells the engine's ten real `source: 'purchase'` blueprints, with a test
asserting each id still exists in `BLUEPRINT_CATALOG` **with that source**, so selling a free
starter blueprint or a deleted one fails rather than shipping. No character SKU: design/14 leaves
the free-vs-paid split of a three-character roster to the store, and that is a product decision.

**A mutation battery over the package, because 98.9% branch coverage is not evidence.** Mutants
scoped to the package's own test files, baseline green first and the revert in `finally`. Round one
was 66 mutants and 59 kills, with three controls surviving as designed and **three real gaps** —
every one of them invisible to coverage. Grown to 84 after the gaps were closed, the battery reads
76 killed and 8 survived, those 8 being six inert controls and two recorded equivalents.
The **ledger claim** was redundant with the order-holder check that runs after it in every scenario
a test had written; the state that reaches only the claim is a ledger row with **no order holding
that transaction id**, which is exactly what a hand-issued support grant produces (and what the
code's own retired-SKU error line tells an operator to do). **Schema constraints had no tests at
all** — relaxing `receipts.product` to nullable survived everything, because nothing ever tried to
write the row without one. And the **oversized-body test was passing for the wrong reason**: it
posted 300 KB via `fetch` and got its 400, and it still got one with the `overflow` flag deleted,
because a truncated prefix of one JSON object does not parse. The hole that flag actually closes
needs the *kept* prefix to be independently valid — a complete document, then a chunk that crosses
the cap and is discarded — at which point the handler books a real order from a body it had already
rejected. Reproducing it took `node:http` rather than `fetch` (which frames the body itself), an
awaited flush plus a real timer gap (two back-to-back `write()`s coalesce into one segment), and
the document sized to `cap - 8` (node reads the socket in 64 KB pieces). `matchsvc.ts`'s own
`readJson` has the same shape with **no** flag and a 4 KB cap — a live defect, left for its owner.

A fourth survivor was not a test gap and is recorded as such: deleting `readJson`'s
`req.on('error')` handler changes nothing observable, because on node v26 an aborted request emits
`'aborted'` and `'error'` and never `'end'`, but with no listener node routes it internally rather
than throwing. The line stays — it is `matchsvc.ts`'s idiom and it guards a runtime detail this
file should not depend on — and the finding lives in a comment on the line, so the next reader does
not correctly conclude it is dead and delete it. The raw-socket mid-upload-disconnect case that
came out of the investigation is kept and honestly labelled as *not* pinning it. A fifth: changing
the default port from 8789 to matchsvc's 8788 survived every test, because each case binds port 0
on purpose — a default that everything overrides is invisible to a whole suite, so it is exported
and asserted both as the documented value and as differing from the other two planes.

**One placeholder deleted the same day it was written.** The internal-key check started as a
billsvc-local guard because 8.1's `internalAuth.ts` did not exist yet at this pass's base commit.
It landed mid-pass, so the placeholder is gone and billsvc uses the shared verifier over
`config.ts`'s registry — one namespace, one fail-closed posture, one place to add per-caller keys.
Two things came with the swap: the registry's single entry is named `gameserver` because that was
the first hop to need a key, so the caller label is corrected to the control plane rather than left
saying something false in an audit line; and `x-internal-key` is deliberately **not** advertised in
the CORS preflight, the mirror of design/16's `authorization` bug pointed the other way — every
internal route is process-to-process, so a preflight never needs it and listing it only invites a
browser client to try.

**What is not built, and is not pretending to be.** Nothing calls into 8.2's `entitlements` table
yet: `delivery.ts` is the seam and `ledgerOnlyDelivery` is its default, under which the append-only
ledger row *is* the delivery record. That is the correct behaviour rather than a stub, because the
entitlements table lives in the **control plane's** database file — a different file, so the
single-transaction guarantee cannot span it, and closing the loop is an internal call whose
placement against that transaction boundary is a real design question and not this pass's. §7's
webhook event log, daily reconciliation and anomaly audit (8.5) are untouched, as is 8.6's
`GameRegistry`. `net` `test` `docs`
