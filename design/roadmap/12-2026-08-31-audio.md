## The search and the gate were the same number three times, and never the same ruler (2026-08-31, tools + assets)

*"the SFX are in; now let us talk about background music."* The SFX set had been complete for a day; music had never existed
as anything but a settings slider wired to `setMusicVolume(_v) => {}`. This pass produced the first
two shipped loops and the pipeline that cuts them. **It produced no runtime**: nothing in the client
reads either file, which is stated here because the status boxes are the place that drift.

### The division of labour, decided before any work

I have no audio channel at all — this is stronger than the looking-is-not-evidence problem in
rendering, where a real frame can at least be extracted and sampled. So the pass was split at the
line where measurement stops: **I own the region choice, the level, the loop seam, the byte budget
and the gate; the user owns whether it sounds right.** Both AI masters were generated by the user
from briefs written here, and the two verdicts below are measurements, not opinions.

### What the measurements said about two AI masters

`audit.py`'s existing `spectral()` reads only the first 32768 samples — the entire file for a 100 ms
cue, and **0.68 s of a 4-minute track**. It reported a 343 Hz centroid and a 175964 ms attack for the
first master, both meaningless. A whole-track band analysis was the first thing built, and it found:

- **`Frozen Resonance`** was prompted as a calm crystal-bell menu bed and came back as a **sub-bass
  drone**: 90% of its energy below 109 Hz, 95% below 198 Hz, nothing above 2 kHz, and its 40-49 Hz
  band 13 dB above every other band. Reassigned to `boss`, where dread is the brief.
- **`Crystal Menu`**, generated after `sub-bass`/`drone` went into the exclude list, moved up two
  octaves (40-49 Hz from -21.2 to -66.0 dBFS) and became the menu bed. It still produced **nothing
  above 4 kHz**, so "high register sparkle" has now failed twice in the same direction — that is the
  service's tendency, not a coin flip.
- **Both masters peak at -0.1 dBFS.** The shipped cue set peaks at **-14 to -21**, because it was
  deliberately peak-matched down to the synth voices it replaced. Every AI master needs ~15 dB off
  before it belongs in this mix; that is one number, `MID_TARGET_DBFS = -30`, and the `music` gate
  now enforces it.

One claim from the previous pass had to be corrected: *"deflect and impact live above 2 kHz"* is half
wrong. Measured per band, `deflect` peaks in 2-8 kHz (-32.1) but `impact` (-33.7) and `muzzle` (-22.9)
both peak in **250-2000 Hz**. The band music has to stay out of the way of is 250 Hz-8 kHz, weighted
toward the bottom of that — which is what the level target is measured in.

### The mistake, three times

The region search and the acceptance gate have to be **literally the same measurement**. They were
not, three times running, and each time the search returned a candidate that then failed:

| search said | gate measured | why |
|---|---|---|
| 3.01 dB | 5.61 dB | the search scored a 2 s crossfade window from four 4096-point frames — 16 k of its 96 k samples. Sampling a window is not measuring it. |
| 2.44 dB | 3.39 dB | the gate weighted per-band differences by energy; the search averaged all 30 bands equally. |
| 1.41 dB | 3.69 dB | the search read the *raw* master, but `boss` always gets a low shelf, and attenuating its dominant sub moves the energy weighting onto the mids, where its ends differ more. |

The fix each time was to delete the second implementation, not to retune it: both sides now call
`audit.profile_diff(band_profile(...), band_profile(...))`, and `--search` applies the track's shelf.
Search, extraction and post-encode figures now agree to within 0.02 dB (`menu` 1.15 / 1.15 / 1.15;
`boss` 1.62 / 1.64 / 1.63). The general shape is worth keeping: **a ranking metric that is not the
acceptance metric is a generator of near-misses.**

### The gate that had to be built rather than reused

`audit.py` already had a `loop` class, and it was the wrong gate for this player. It requires
`step_db <= -50` — the last sample sitting next to the first, which is what `el.loop = true` needs —
and MP3 frame padding makes that unavailable regardless. Since track-to-track changes need a
crossfade anyway, the player reuses it to close the loop (a second deck starts at `length - 2 s`), so
the real requirement is that the two ends are **tonally compatible over 2 s**, not continuous.
The new `music` class drops `step_db`, allows stereo (a 69 s bed streams; a 100 ms cue's second
channel is pure overhead), and adds `xfade_band_diff <= 2.5` plus `mid_band_dbfs` in `[-31, -29]`.

Routing had to change too: files reach the `music` class **by directory**, because a track named
`menu.mp3` matches no cue prefix, fell through to the caller's default, and both beds were reported
as "too long" and "stereo wastes bytes" — the same shape as the `pickup.*` mis-routing this gate
already had a regression test for.

### Four bugs the checks caught, and one they did not

Every measurement here was checked against synthetic signals with known answers, and four of the
five things that were wrong were found that way, not by reading:

- **An FFT normalisation that calibrated peak amplitude while reporting RMS** (a 100 Hz sine read
  -4.44 dB where -6.02 was expected; the honest expectation was -9.03, and the assertion was as wrong
  as the code).
- **A block loop that never executed on short input.** `band_rms` used a fixed 65536-sample block, so
  every 0.1 s cue read `-inf` in every band — which looks exactly like "this cue has no energy" rather
  than "nothing was measured".
- **An empty band returning `-inf`**, so differencing two profiles gave `nan`. Real inputs hit this:
  after resampling, every band above the new Nyquist is exactly zero. `nan` also fails `< limit` *and*
  fails `> limit`, so the assertion phrasing mattered — `assert x < 0.5` caught it where
  `assert not (x > 0.5)` would have passed.
- **A 2nd-order low shelf that under-delivered where it was aimed**: -6.9 dB at 40 Hz for a -14 dB
  shelf at 80 Hz, when 40-49 Hz was the exact band it existed to tame. Now 4th-order, and the
  selfcheck asserts the *requirement* (near-full cut by f0/2, unity by 4·f0, monotonic between)
  rather than restating the algebra.
- **The one the checks did not catch**, because it was mine and outside the tool: `pathlib.write_text()`
  uses the Windows locale encoding, so a doc patch wrote cp1252 em-dashes into a UTF-8 file *and*
  silently failed every replacement pattern containing one — 4 of 5 edits no-oped and the file was
  left invalid UTF-8. Explicit `encoding="utf-8"` on both ends, plus a decode check after writing.

An honest note on `xfade_band_diff`'s weighting, since it is the number everything else keys off:
unweighted, it averaged 30 bands equally, so bands near -100 dBFS — where the only content is FFT
leakage whose phase differs between the two windows — dominated the result. A two-sine bed whose
head and tail were **identical by construction** measured 6.12 dB that way, enough to fail a 3.5 dB
gate on nothing at all. Weighted by the louder of each band's two windows, the same fixture reads
0.01 dB.

### The byte gate went off, and what it found underneath

Dropping 1.09 MB into `client/public/audio/music/` failed `npm run check` immediately: with no
rule in `assetPacks.json` the files fall to `defaultPack: "main"`, and the WeChat main package
went from 4.00 to **5.09 MB against a hard 4.00 MB limit**. design/11 had already predicted the
fix ("a future music subpackage is a prefix rule in `assetPacks.json`, not a loader change") and
that is exactly what it took: one pack entry, one `/audio/music/` prefix rule, no loader and no
manifest change. `SUBPACKS` is derived from that file, so `ensureAllPacks()` will call
`wx.loadSubpackage` for it at boot with no further wiring.

That pack is justified differently from the four before it, and the `$comment` block now says so.
The biome and boss packs are deferred because their contents are **unreachable** in a fresh run;
`menu` is wanted on the very first screen. Music is deferred purely on **bytes** — it is the one
asset class a game can start without.

**What the gate found underneath is worse than what it was reporting.** With music moved out,
main measures **4,191,575 of 4,194,304 bytes — 2,729 bytes of headroom**, 99.93% full. Nothing
in this pass caused it (music is in its own pack; main's assets are 3.24 MB and the code bundle
0.95 MB), and the last recorded figure was 3.42 MB on 2026-08-30, so ~770 kB arrived from other
work since. Two things follow. First, **the next code change of any size fails this gate**, which
matters immediately because the music *runtime* is the next pass and it lands in `js/game.js`.
Second, the gate measures **uncompressed**: the checker's own note says main is ~3.36 MB gzipped,
so if WeChat bills the compressed package there is real slack and the emergency is with our
measure rather than with the platform. Which of those two it is has never been checked on a
device — the same open item as every other WeChat audio question here.

## Everything existed and nothing was connected (2026-08-31, client runtime)

*"build DayDayUp's background-music runtime out in full ... right now the game has no music at all."* Same day as the pass above, and
the complement to it. That one produced 1.09 MB of gated, documented, subpackaged assets and stated
plainly that it produced no runtime. This is the runtime.

The state it started from is worth naming precisely, because it is a failure mode rather than an
oversight: **every individual piece existed and passed its own check.** The files were cut, measured
and gated. `assetPacks.json` had a `music` pack with a `/audio/music/` prefix rule. `audit.py` had a
`music` class. `art/audio/README.md` had a table with per-track rationale. `settingsBinding.ts`
computed the music volume and pushed it down every time the player moved the slider. `design/11` had
a locked decisions list. The whole suite was green. And the game was silent, because
`setMusicVolume` was `(_v) => {}` in both backends and nothing ever opened either file. No unit test
in the repo could have failed on that — there was nothing wrong with any unit.

### The blocker was 2,729 bytes, and it was settled before any code

The previous pass ended by noting that the WeChat main package sat at **4,191,575 / 4,194,304
bytes** and that the music runtime was code landing in `js/game.js`. It named two roads: move art
out of main, or establish that WeChat bills the COMPRESSED package (the gate's own note estimates
main at ~2.78 MB gzipped, so there would be real slack).

**The second road was not opened, and that is a finding, not a deferral.** The only authoritative
source is DevTools' upload dialog, which needs a registered appid and a logged-in session — and
pressing upload *publishes the package*. So the gate still measures raw bytes, which is the
conservative direction, and this joins every other WeChat audio item on the needs-a-device list.

The first road took one pack and one rule, and the interesting part was *what* to move. The
`$comment` in `assetPacks.json` states the criterion as "art that is unreachable in a fresh run",
and by that criterion **almost nothing in main qualifies**: `hub_bg` is the backdrop of the LOGIN
screen, every weapon can drop on floor 1, `brute`/`floater` spawn on floor 1, and both alternate
character rigs are pickable from the start. Checked against the shipped content rather than assumed,
the way that comment asks for.

What the gate found instead is that one file is simply out of line with its role:
`environment/door_curtain_raw.png`, **606 kB** — 468x832 of translucent gradient that compresses to
1.56 bytes per pixel, **12x the next door state** (`door_locked_raw`, 50 kB) for one fixture. So it
moved into a new `oversized` pack, justified on **bytes** exactly as `music` itself was, with the
reachability argument explicitly disclaimed rather than fudged. Main went to **3.42 MB / 4.00 MB**,
610 kB of headroom. Two notes went with it: the real fix is a re-encode, which changes how the
curtain LOOKS and is therefore a call a person has to make; and when that lands the pack should be
**deleted rather than refilled**, because a pack named for a symptom becomes a dumping ground if it
is allowed to persist empty. `assetManifest.test.ts` already asserted "every environment sprite is
in main", so the exception is now listed there by NAME — a second deferred environment sprite still
fails that test.

### What the runtime is

- **`audio/musicCatalogue.ts`** — `MusicTrack` in `platform/types.ts` beside `AudioCue`, an
  exhaustive `Record<MusicTrack, TrackDef>` here. Same split, same guarantee: a new track is a
  compile error until it has a file, a length, a gain and an answer to "is this file really yours".
- **`audio/MusicPlayer.ts`** — two decks, one equal-power crossfade, and the point of the design:
  **the loop is a track change onto the same file.** `el.loop = true` cannot be used (MP3 frame
  padding denies the sample-exact wrap every native looping API performs), so the second deck starts
  at `length - XFADE_S` and fades across. One envelope, both behaviours, both exercised by the same
  tests.
- **Two platform decks**, which are the only per-platform code and differ structurally. Web:
  element → `createMediaElementSource` → deck gain → music bus → destination. WeChat: an
  `InnerAudioContext` with **no audio graph at all**, so the settings volume must be multiplied into
  each stream's own `.volume` alongside its fade. That is the whole reason `setMusicVolume`'s two
  implementations can never be shared, and it was worth writing down as the answer to "why isn't
  this one method".
- **`game/musicDirector.ts`** — derives the track from (phase, live state, our seat's room) every
  frame. No engine events, no sink, no trigger.
- **Real `setMusicVolume`**, plus `visibilitychange` on web and `wx.onAudioInterruptionBegin/End` on
  WeChat. Neither platform had ever wired focus handling for audio at all.

### Four decisions that are not obvious

- **`dungeon.ember` borrows `menu.mp3`, not `boss.mp3`.** It has no master, and `boss` is the closer
  match in mood — which is exactly why it is the wrong loan. With one file on both sides of the boss
  room's threshold there is no audible change, and *"the music never switches"* is
  indistinguishable from *"the music feature is broken"*. A bed that is wrong for the room is a
  taste complaint; a transition nobody can hear is a bug report. The substitution is a FIELD
  (`TrackDef.borrowedFrom`), not a comment, so which tracks are standing in is derived and
  assertable — a stand-in recorded only in prose is a stand-in that ships forever.
- **The wrap point is READ BACK from the deck, never counted.** `dtMs` drives the envelope; `pos`
  comes from the stream. An accumulated clock drifts on every stalled frame and it drifts silently:
  the symptom is a crossfade that starts before or after the seam, which sounds like a badly cut
  asset rather than like a bug in a counter. This paid for itself immediately during browser
  verification — see below.
- **Boss music keys off `RoomPiece.role === 'boss'`, not off a live boss existing.** The bed changes
  as the door is crossed rather than when the first spawn lands, and stays changed while the player
  picks up the boss's death drops instead of snapping back over the corpse. A player mid-passage has
  no `roomId`, which reads as "not the boss room" — the alternative (remember the last room) would
  hold boss music through the door OUT of it.
- **`Game.ts` was not touched.** The tick lives in `GameLoop.update` (before the phase branch, so
  the MENU bed is driven at all) and reaches the device through a module sink attached at boot — the
  `uiSound.ts` shape, for the `uiSound.ts` reason plus a hard one: the length gate pins `Game.ts`
  at its recorded size, so a new dep in its `GameLoopDeps` literal fails `npm run check`.

### The gate the loops had never had

`platform/audioAssets.test.ts` reads `public/audio/` with a **non-recursive** `readdirSync`. Nobody
decided that music should be exempt from it; the loops shipped into a subdirectory and fell out of
its byte budget, its credits cross-check, its format check and its licence sweep, all at once and
silently. `audio/musicAssets.test.ts` is the replacement, and three of its rules are inversions
rather than copies:

- **Stereo is REQUIRED**, where the cue gate requires mono. If those two assertions ever agree, one
  of them has been broken.
- **The length is load-bearing.** It is what places the crossfade, so it is checked against the
  file's real audible duration (MPEG frame level, no decoder) to 50 ms. The frame walker moved out
  of the cue test into `audio/mp3Frames.ts` so there is ONE of it — two copies of an independent
  second opinion is one copy of it.
- **The licence is not CC0**, so it cannot go through `packs.json` (whose every entry the cue test
  asserts is CC0). `credits.json` grew `music`/`music_terms`, and what the test holds is that the
  record stays **honest about what it lacks**: the verbatim prompt was never captured and no licence
  text is archived, both pinned as declared gaps. A test demanding they be filled would only invite
  them to be filled with a guess.

Plus a cross-check that had no owner before: **`XFADE_S` is read out of `audit.py`** and asserted
equal to the player's. That number is the width of the window `xfade_band_diff` measures, so the
shipped 1.15 dB / 1.63 dB figures ARE that measurement — and both sides stay internally consistent
if it moves on one of them. Same shape as this thread's own three-times mistake, one layer up.

### Measured, because I cannot hear it

Real browser, real graph, real files. After the first gesture: `menu.mp3` arrives as a **206 Partial
Content** range request (genuinely streaming, not fetched whole), one deck live reporting
`duration: 69` exactly matching the catalogue, `loop: false`, deck gain rising 0.10 → 1.00 across

**One incidental finding, and it is the position-read design paying for itself.** In that embedded
browser pane `requestAnimationFrame` is suspended while `document.hidden` stays *false*, so the
entire game loop freezes while audio keeps streaming — 0 frames in 3 s, measured. The bed ran to its
end and went quiet, and then **the wrap fired on the first frame that ran**, because
`pos >= length - XFADE_S` was still true. A counter-driven wrap would have fired somewhere in the
middle of nothing and never recovered. Worth stating what this is not: a bug to fix. A frozen loop
means the sim, the renderer and the fx are frozen too; music going quiet with them is consistent,
and it self-heals.

## The parser every audio gate trusted had no test, and its own header was wrong (2026-09-01, tests)

A follow-up pass on the music thread above, asked as "see whether there are tests worth adding" — are there tests worth

### Three gaps, found by asking what the tests are FED rather than what they assert

- **`audio/mp3Frames.ts` had no test of its own.** It is the independent second opinion behind
  `platform/audioAssets.test.ts` (50 cues), `audio/musicAssets.test.ts` (2 loops) and one
  `musicPipeline` case — and all three feed it the 52 files that are already **correct**. That leaves

- **`platform/wechat/weChatMusicDeck.ts` had no unit test**, while its web counterpart had one —
  written after the battery above found `position()` unguarded there. The WeChat deck was in exactly
  that state, plus the `playing` state machine around `stop`/`setPaused`/`position`, and the one
  behaviour with no web counterpart: restarting an unchanged `src` via `stop()` then `play()`, which
  IS how the second deck begins the loop wrap.
- **Two tests asserted a contract that had stopped being true.** Both backends still carried
  *"setMusicVolume accepts a value and does nothing (music not authored yet)"* — green, and false
  since the pass above. Replaced with the one thing the integration files do not cover: neither method
  may construct its context or open its streams, because `settingsBinding.load()` calls it at boot,
  before the gesture on web and before `wx.loadSubpackage` has run on WeChat.

### The walker's header claimed a check it never had

Writing the truncation case is what found it. The comment said a truncated file "fails as itself";
the first version of the test asserted that and **failed against the code**. The reason generalises:
frames are a fixed length at a constant bitrate, so a cut always leaves an intact header at the last
boundary, `i += len` steps past the end of the buffer, and the loop ends cleanly with the stub counted
as a whole frame. `lost frame sync` cannot fire for truncation at all.

Fixed with two rules — a frame declaring more bytes than remain, and a trailing stub too short to be
a header — but **only after measuring the population the rule would apply to**: all 52 shipped files
plus both Suno masters end on an exact frame boundary, so the strict form rejects nothing real. A
strict rule is a guess until that measurement exists. One shape stays uncatchable on purpose: a cut
AT a frame boundary is byte-for-byte a valid shorter file, and nothing in the bitstream can say
otherwise — which is exactly why `credits.json`'s byte-size cross-check is not redundant beside a
parser that walks every frame.

A second bug in the same file, found while testing the first: the frame-length guard read `len <= 4`,
and both reserved header indices together make `len` **NaN**. `NaN <= 4` is false, so the guard let it
through to `i += NaN` — which exits the walk quietly and reports a frame count plus a duration divided
by a zero sample rate. Now `!(len > 4)`.

### The battery refuted a change I had already made

The second finding was reported as *dead code*: no combination the parser accepts can describe a frame
shorter than 24 bytes (measured over all 252 of them), so the `len <= 4` guard could never fire and no
test could cover it. It was deleted, with an invariant test over the whole table standing in for it.

The mutation battery refuted that within the hour. With the guard gone, the mutant that disables the
reserved-index check stopped failing a test and started **hanging the suite** — a free-format bitrate
index gives `len` 0, so `i += len` never advances. The guard is back, `NaN`-safe, and the invariant
test now states what it rests on instead of replacing it. Two things worth carrying forward: **an
unreachable branch that converts a hang into a thrown error earns its line**, and when a guard looks
dead the question is what happens to the LOOP without it, not only which input reaches it. The harness
learned something too — a run without a per-process timeout sat on that hang for minutes reporting
nothing, and any wrapper judging by exit code alone would have scored it `killed`. A hang is not a
kill; it means the tests never got to judge the mutant.
