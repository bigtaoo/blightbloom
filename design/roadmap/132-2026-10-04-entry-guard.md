## One shared run-as-main block, and a failed boot is one log line (2026-10-04, server + test + docs, no ENGINE_VERSION change)

The last uncovered lines in `matchsvc.ts` and `index.ts` were the run-as-main blocks:
`if (process.argv[1] && fileURLToPath(import.meta.url) === process.argv[1]) { ... }`.
Volume 131 added the process guard to all five of them, which moved the same gap into
`billsvc/main.ts`, `adminsvc/main.ts` and `backup/main.ts` too.

### Why they could not be covered

Inside the vitest worker the condition is false by construction, since `argv[1]` is vitest.
A spawned child is not counted either, because v8 coverage does not collect from child
processes. The five blocks also disagreed on what a failed boot prints:

- matchsvc and adminsvc printed a one-line `console.error`.
- billsvc printed `console.error(e)`, a raw multi-line stack. Volume 131 left this open.
- backup and the gameserver printed nothing of their own.

### The change

`src/entry.ts` exports `runAsEntry(import.meta.url, tag, start)`, and each entry point's block
is now that one call. It does three things:

1. It compares the module path with `argv[1]`.
2. It installs the process guard with the service's logger.
3. It calls `start()` with no arguments, so each `main` reads the environment through its own
   parameter defaults. `backup/main.ts`'s `main` gained those defaults.

The entry check, the logger, the guard's `process.on` and `process.exit`, and the exit-code
setter are all injectable. That is what makes both arms testable.

A boot that rejects or throws becomes one `ERROR [tag] failed to start` line, written through
the service's logger with the stack as a field, and sets `process.exitCode = 1`.

adminsvc still boots through `runMain`. That keeps its config refusal
(`[blightbloom] adminsvc refused to start: ...`) as a stackless line naming the fix.

### Tests

- **`entry.test.ts`** drives both arms with everything injected:
  - not the entry: nothing runs and no guard is installed;
  - the guard is installed before `start`, and `start` is called with zero arguments;
  - a rejected boot and a synchronously thrown boot both produce one line and exit code 1;
  - a boot that resolves leaves the exit code alone.

  One case runs with nothing injected, stubbing `process.on` and `process.exit`. It covers the
  production defaults, including the two default lines in `processGuard.ts`.
- **`deploy.bundle.test.ts`** boots matchsvc, billsvc and backup against an unreachable cluster.
  Each must exit 1, print the tagged `failed to start` line and print no `    at ...` line.
  - adminsvc is left out because it boots read-only without a cluster.
  - The gameserver is left out because its boot touches no database.
- **The adminsvc refusal test** now also requires the `refused to start` line and no
  `failed to start`. That pins that the bundle boots through `runMain`.
- **14 of 14 mutants fail the suite**:
  - in `entry.ts`: the guard dropped; the guard's injected deps dropped; the entry check
    inverted; `exitCode` 0; `exitCode` not set; `start` given an argument; `warn` instead of
    `error`; the stack dropped from the line;
  - each of the five `runAsEntry` calls removed or retargeted. A first run left adminsvc's
    `runMain` → `main` swap alive, which is what the refusal assertion above now kills;
  - backup's `argv` default emptied.

Server coverage moved from 99.25% to 99.71% lines and from 98.41% to 98.78% branches.
`entry.ts`, `processGuard.ts`, `matchsvc.ts` and the billsvc and adminsvc `main.ts` are now
fully covered.
