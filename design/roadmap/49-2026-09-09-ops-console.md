# Work log — 2026-09-09

## A console that cannot write, and a flag that does nothing (2026-09-09, server + deploy + docs, no engine change)

Volume 48 designed three phases and shipped the first. This is B and C: the read-only
console at `bb.gamestao.com/admin/`, and feature flags. Both were specified in
[design/21-ops-analytics.md](../21-ops-analytics.md) before a line was written, which is
why most of what follows is about the two places the specification turned out to be wrong
and the one place it was right in a way that cost a design change.

### Phase B — adminsvc, and why "cannot" is a different claim from "does not"

A fifth process (`server/src/adminsvc/`, 8790), because matchsvc is the one service Caddy
proxies wholesale — a route added there is public the moment it exists, which is why
`/metrics` had to explicitly refuse proxied requests. Building the panel there would make
every future admin route inherit *public unless it remembers not to be*.

The property that makes a publicly-exposed console proportionate is decision B1, and the
form of the sentence matters: **it is not that the console does not write player data, it is
that it cannot.** `accounts.db`, `billing.db` and `analytics.db` are opened `readOnly: true`,
enforced by SQLite, and in the deploy the same two directories are `:ro` bind mounts — so it
is refused twice, once by the kernel and once by the database. `adminsvc.dbs.test.ts` asserts
it the only way that claim can be asserted: it ATTEMPTS an INSERT, an UPDATE, a DELETE and a
DROP through each handle and requires each to throw, with a `SELECT` beside them as the
control. A test that checked the option was passed would pass against a handle that ignored
it.

**Every handle is nullable, and none of the three nulls is defensive.** `readOnly` mode does
not create a missing file — it throws — and all three files belong to other processes:
`analytics.db` does not exist until collection is switched on, `billing.db` until billsvc has
booted once, `accounts.db` until somebody registers. So the console comes up with per-section
"unavailable" cards carrying the reason, and the `deploy.bundle.test.ts` case that proves it
boots the real bundle with none of the three present. A process that refused to start could
not be used to find out why the file is not there.

### The three views, and the one the design got wrong

**Players** — search by username or display name, a row per account with provider, created,
rating, entitlements and last-active. §3.2 said last-active comes from `daily_active`; that
table cannot answer it. Its columns are `(day, install, host)` and it holds **no account id
at all**, by design, because a retention cohort is a question about a browser and joining it
to an account would assemble exactly the profile §2.1 promises not to. The link exists only
on `events.account_id`, which the server attaches from the bearer. That has a consequence
worth stating on the page rather than hiding: `events` is pruned at 90 days, so a blank cell
means *no event in the window*, never *never played* — and a column that conflated those
would be read as the second one.

The search's LIKE wildcards are escaped, and that guard has its own test because the failure
looks like a typo: without it, a search for `%` returns the whole accounts table and `_`
returns every one-character username. The count query and the row query both escape, because
a count that forgot would render "1 shown of 5 matching" — a lie in the direction nobody
checks.

**Commerce** — `review_queue` and `webhook_events`, which billsvc has written since
2026-09-05 with nothing to read them through. Open findings are their own query, oldest
first, because a single time-ordered list buries the two open items under three hundred
reviewed ones the day the table has any history. `divergences` is counted over the WHOLE
table and printed above the page, since a non-zero count whose row is not on screen is the
one case a per-row flag misses.

**Retention** — the `daily_rollup` cohort grid, A5's answer to Prometheus's 15-day window
and the only section that is not a convenience. One rule runs through it: `rollup.ts` refuses
to emit a gauge for an unaged cohort, so the grid's empty cells arrive as MISSING ROWS, and a
grid that rendered a missing row as `0%` would say *nobody came back* for every cohort in a
launch week. `CohortCell` is therefore `{rate, size} | null`, and the test fixture is built by
running the shipped `persistRollup` once per simulated day so the grid contains a measured
`50%`, a measured `0%` and an unknown side by side. The page prints the rollup row count too:
an empty grid over zero rows is an empty database, and an empty grid over three hundred is a
bug in the reader.

### The XSS this console is actually exposed to

`webhook_events.raw` is a verbatim copy of bytes an outside party POSTed to the billing
plane, and the console renders it. That makes this a page where attacker-authored text is
displayed in the browser of the one account that can read every player's row. The rule is
structural rather than careful: the view modules deliberately do NOT pre-escape, so there is
no "already safe" category to reason about, and `page/layout.ts`'s `esc` is the single gate.
`adminsvc.http.test.ts` drives the whole chain — a `<script>` written into the real billing
schema, read through the real read-only handle, rendered by the real page — and asserts it
comes back as text. `default-src 'none'` sits on top, which is also why the shell test asserts
the page references no script, no font and no image at all.

### Auth, and the two things a test found in the writing

One credential from the environment, no self-registration, no reset (rotation is an env
change plus a redeploy — B3). `credentialMatches` hashes both halves before
`timingSafeEqual` and compares both without short-circuiting, so neither the password's
length nor which half was wrong is measurable. `assertAdminStartupSafety` throws before
anything is opened or bound, and `deploy.bundle.test.ts` proves it against the artifact: a
bundle with no `BB_ADMIN_PASSWORD` must exit 1 naming the fix, not listen with a default.

`Secure` on the session cookie has a dev-only relaxation, refused under
`NODE_ENV=production` by the same guard — because the alternative to having one is somebody
commenting the attribute out locally and shipping that. `Path=/admin` is the one cookie
attribute chosen for something other than its own security: the game and the console are one
origin behind Caddy, so a `Path=/` cookie would ride along on every player's
`POST /client/events`.

**A test caught a real bug in the retention tooltip.** It read
`${cell.size} of ${row.dau} installs returned`, which rendered "4 of 4" on a 50% cell —
`daily_rollup` stores the rate and the cohort size and **not** the return count, so there was
no numerator to print. A cell whose tooltip contradicts its own percentage is the kind of
instrument that gets believed.

### Phase C — flags, and the switch that did nothing

`ops.db` in adminsvc, an internal `x-internal-key` endpoint services poll, and a merge over
compiled-in defaults. Fail-safe by construction rather than by care: a service never opens
`ops.db`, it holds a `FlagValues` object that starts as `defaultFlags()` and is replaced only
by a complete usable answer. `flags.client.test.ts` walks every way a poll can fail —
unreachable, 401, 503, an HTML error page, an empty body, a payload missing one name, a
payload with one value out of range — and requires each to leave the previous values in
place, with a successful poll as the control.

The parse is **all-or-nothing** on purpose. A partial merge would let a garbled response turn
one flag off and leave the rest, which is a state nobody configured and nobody could
reproduce — including silently reverting a deliberate override because a *different* flag's
value was corrupt.

C1 is the allowlist, and it is enforced on both sides of the table: `setFlag` will not write
a name that is not in code, and `readOverrides` will not return one — the two are edited by
different people at different times. `flags.defs.test.ts` pins the exact set of names, which
is deliberately the kind of test that would normally be a smell: it is the mechanism, not a
check. Adding a flag fails the suite, and the only way past it is to say in a review which
side of C1's line the new one falls on. Beside it, a pattern test refuses any flag whose NAME
contains `auth`, `stub`, `verif`, `secret`, `key`, `password` or `admin`, because a list of
forbidden names is a list somebody has to have thought of.

**A flag captured at construction is not a flag.** `Matchmaker` took `queueTtlMs` and
`pvpBotFillMs` as numbers and captured them in its constructor, so a console change would
only take effect on the next restart — i.e. a differently-spelled deploy. Both now accept a
supplier, read per decision, and a test asserts a value polled AFTER the server was built
changes the next answer.

### The gap the design did not name

Two of the four flags are about the CLIENT — the rewarded-ad offer and a maintenance banner —
and §4's delivery mechanism is an `x-internal-key` endpoint a browser cannot call and must
never be able to. So those two have a row in `ops.db`, a control in the console, and nothing
on the other end.

**A switch that looks live and changes nothing is the worst thing an ops panel can contain**,
and this project has paid for the shape once already: volume 47's "errors by build version"
panel was fully populated and meaningless because nothing could supply the field. So the
state is carried in the TYPE (`FlagDef.consumer` / `delivered`), rendered as a per-row
`not delivered` badge with a warning above the table, and `flags.defs.test.ts` pins which two
they are — so it cannot be "fixed" by flipping the boolean instead of building the path. The
alternative, deleting the two flags until a delivery path exists, would also have deleted the
boolean and string arms of `coerceFlag`: tested validation for the two shapes the first real
client flag will need. **What it needs is a PUBLIC field on a response the client already
fetches, and that is not built — see design/21 §9.**

### Coverage, and the branches that were removed rather than tested

Every new module landed at **100% lines and 100% branches** except `adminsvc/main.ts`, whose
one uncovered branch is the `require.main === module` guard no in-process test can reach —
21/22, which is the best of the five entry points in this repo (index.ts is 73/80).

Getting there deleted five branches instead of testing them, and each deletion is the same
argument: **a branch no input can reach is something a coverage gate cannot tell apart from
one nobody tested**, so it is the shape that gets deleted in a refactor with nothing going
red. `AdminDbs.errors` became a TOTAL record with `''` for an opened handle, which removed a
`?? ''` at every call site; the cohort sort became `b.localeCompare(a)`, because `Map` keys
are distinct so a hand-written comparator's third arm is unreachable; `coerceFlag`'s
`range === undefined` and `maxLength ?? 0` became assertions backed by a test over the whole
allowlist; `timer.unref?.()` became `timer.unref()`; and `flagRoutes`' verifier became
REQUIRED rather than defaulting to an empty registry — so "forgot the verifier" is a compile
error rather than a silently-open route.

Two seams exist only so that a type's `undefined` is reachable honestly: `requestTarget`
takes the narrow `Pick<>` it needs (Node always sets `url` and `method`, so those fallbacks
cannot be reached through a socket), and `FlagsView.undelivered` is passed in rather than
derived from `FLAG_DEFS`, which makes the *everything is delivered* state — the one this
project should reach — testable before it arrives.

### What RUNNING it found

Written before the console had ever been looked at, so it was looked at:
`server/scripts/seedOpsDemo.ts` seeds the four databases through this repo's own openers and
fills each section with the states worth seeing rather than the states a fresh box has.

**The audit line stamped `operator=admin` on requests that carried no session** — a health
probe, a stray `/favicon.ico`, a *rejected login*. The field is the configured operator name
and not the requester, so those lines asserted that the operator made a request they did not
make, which in an audit trail is the one distinction that has to survive. The test that
produced that line was already green: it asserted the fields that are present and never the
field that should be **absent**. Fixed, and the test now asserts the absence.

The rest of the run was confirmation rather than discovery, and it is the half no assertion
covers: the cohort diagonal fills from the left, `0.0%` and `—` are visibly different things
in the same column, the 502 HTML body renders as text in the webhook column, and a value
typed into the real form reached `GET /internal/flags`. Two notes for next time —
`BB_ADMIN_INSECURE_COOKIE=1` is required to sign in over plain http (which is what that flag
is for), and `tsx` must run from `server/` or the `@dd/*` aliases do not resolve, because
`config.ts` pulls in `@dd/game/match/pvpConfig` and adminsvc inherits that through the
internal-key registry.

### Deploy

A fifth esbuild entry, a compose service, `HTTP_SERVICES` in the manifest gate, and one Caddy
`handle /admin*` block ahead of the catch-all. §3.4's named trap turned out already answered
in practice: the site block became mutually-exclusive `handle` blocks when Grafana landed, so
first-match ordering is what the file says. `/admin/health` refuses a request carrying
`x-forwarded-for` the way `/metrics` does, since Caddy proxies the prefix wholesale.

`ops.db` gets its OWN writable mount, deliberately not under `/sources/`, so the path in
every log line says which kind of handle it is — and the manifest test asserts adminsvc's
three mounts as a PARTITION (two `:ro`, one writable) rather than as "all read-only", which
stopped being true when Phase C landed. `ci-deploy.sh` normalises the new state directory's
ownership, because Docker creates a missing bind-mount source `root:root` and the mount then
hides the image's own `chown` — the failure that cost this deployment 18 hours of silent
backup failures on 2026-09-08.

`ops.db` is deliberately **not** a fourth backup source. Every row in it is a value an
operator typed over a default that is in git, so its loss costs the current override set —
which the console shows and a human can retype in a minute. The other three hold identity,
money and measurement.

### Two files split, one of them not mine

`matchsvc.ts` crossed 500 lines when the flag wiring landed, so `matchsvcMetrics.ts` came out
as a sibling of free functions with the original path kept alive as a re-export. And
`RateLimiter`/`clientKey` moved out of `routes/telemetry.ts` into `rateLimit.ts` — because
reaching for the limiter from adminsvc through that file would have pulled the Loki push, the
analytics ingest and the client-log parser into the console's bundle for one class. What is
reused is the MECHANISM; the budgets differ (20/minute for telemetry, 10 per five minutes for
a login, where the legitimate rate is one per working day).
