## A Host header that does not parse is a 400 (2026-10-04, server + test + docs, no ENGINE_VERSION change)

Found while bringing `matchsvc.ts` up from 69.7% lines, whose request error boundary had a
synchronous arm no test reached. The one real way to reach it was a request whose `Host` header
`new URL` cannot parse: `a b`, `[`, or a port past 65535. matchsvc answered that with a 500 and
an ERROR log line. Then the other three services were probed with the same request.

### What each service did

Each builds its routing URL as `new URL(req.url, 'http://' + req.headers.host)`, so the
client's Host header is part of the parse, and `new URL` throws on a host it cannot read.

| Service | Where the parse ran | What a bad Host did |
|---|---|---|
| matchsvc | inside its error boundary | 500 and an ERROR line |
| billsvc | the request listener, no boundary | uncaught exception |
| adminsvc | `requestTarget`, before its boundary | uncaught exception |
| gameserver | the socket's `connection` event, after the upgrade | uncaught exception |

No process installs an `uncaughtException` handler, so the last three would exit on one request.

### Why production was not exposed

Caddy routes only a request whose host matches its one site block, `bb.gamestao.com`, so a
request with an unparseable Host never reaches a service from outside. It could still come from
anything that reaches a port directly. A service's correctness should not rest on the proxy in
front of it, and the fix is a few lines.

### The fix

`src/requestUrl.ts` builds the URL with `URL.parse`, which returns `null` rather than throwing.
All four services use it:

- matchsvc, billsvc and adminsvc answer `null` with `400 {"error":"bad request"}`. It is the
  client's request that is wrong, so it is neither a 500 nor worth an ERROR line.
- The gameserver refuses the WebSocket handshake with a 400 in `verifyClient`, before the
  upgrade, so its `connection` handler only ever sees a URL that parses.

matchsvc's synchronous try/catch stays, since any future synchronous bug in the route chain
lands there. Its only test now uses a stand-in `dispatch`.

### Tests

- `badHost.http.test.ts` sends three bad hosts to each of the four services over a raw socket.
  `fetch` will not send an invalid Host. Each must answer 400 with nothing logged at ERROR,
  then serve the same request with a sane host.
  - Run against the code before the fix, all four cases failed. billsvc, adminsvc and the
    gameserver raised the uncaught `Invalid URL` exceptions.
- `adminsvc.transport.test.ts` pins `requestTarget` answering `null`.
- `matchsvc.errorBoundary.standin.test.ts`, renamed from `.sent`, drives both of the boundary's
  unreachable arms with a stand-in `dispatch`:
  - a synchronous throw;
  - a failure after the response has started.
- Each fix point's mutant fails the suite, 7 of 7: each of the four guards removed, the 400
  turned into a 500, `verifyClient` answering without the status, and `URL.parse` swapped back
  to `new URL`.

The `main()` pass earlier the same day was test-only and has no volume of its own. Its tests,
`matchsvc.main.test.ts` and the boundary cases, are in commit `9c52d43`.
