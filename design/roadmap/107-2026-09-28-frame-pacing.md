## Every second holds the same frame rate, on a slow CPU too (2026-09-28, client + perf + test + tools + docs, no engine change)

The owner's requirement: *"每秒内的帧率差距不超过3"* — the frame count of any one second may differ
from any other's by at most 3. At first that meant the 1080p desktop; after the desktop passed, it
meant a phone as well. A 4x CPU throttle in Chrome stood in for the phone. This entry covers five
branches that landed on the day, in order, and then the guard that keeps them.

### The doorway drop: `room_enter` stops rebuilding the floor it is on

A floor is one co-resident map, placed when it is generated. Even so, `room_enter` — the first step
into each room — rebuilt ALL of it: about 11 ms of build, plus about 12 ms of re-triangulation in the
next render. Every doorway dropped a frame or two on a machine that otherwise held 60/60.

The rebuild drew the same floor. Mid-floor, `state.walls` changes only by a locked door's own passage
rect, which `build()` already skips, and `updateDoors()` restyles the fixtures on the door events that
follow. Frame-diffed live, a same-floor rebuild changes 0 pixels. It was also what defeated the door's
lock crossfade: it rebuilt the door already locked.

`RoomBuilder.enterRoom` now rebuilds only when `scene/floorKey.ts` says the floor changed: a different
state, a different floor index, or a different first placed room. `clear()` drops the key.
`scene/portalPlacement.ts` was split out to keep `RoomBuilder` under 500 lines.

### Four frame-shaped costs: allocation, the descend, the run start, shader links

- **Allocation.** A run allocated about 15.7 MB/s, most of it inside Pixi re-triangulating Graphics
  the client cleared and redrew every frame whether anything had changed or not.
  - The minimap now redraws a layer only when its own content changed.
  - A HUD bar now refills only when its fraction moved.
  - A door's motes, pulse and burst are now cleared only when non-empty.
  - Rig tethers and contact shades are built once and posed by transform.

  Result: about 5.2 MB/s, and GCs per 30 s down from about 30 to 6–8.
- **The descend.** The whole new floor was built in the frame its `room_enter` landed, a 48 ms frame
  every descend. `scene/stagedBuild.ts` now runs the build as a queue of steps, a few ms per frame,
  behind `scene/descendCover.ts` (a cut to black under the HUD, then a 280 ms fade back in). The step
  that plans the walls is `scene/roomWallPlan.ts`, split out as a pure function. Worst frame 48 to
  about 12–14 ms, with no dropped vsync.
- **The run start.** The run-boundary loading screen came down BEFORE the run's one-time costs, so
  they landed on the first visible frames: 132 ms frames, 44–46 frames in the first second.
  `controllers/TransitionGate.ts` now keeps the screen up until a run of consecutive frames is within
  1.5x the fastest seen, which is the device's own vsync. First visible seconds now read 60, 60, 60.
- **Shader links.** Pixi links a filter's program the first time something draws through it, and
  does so synchronously. The outline and dissolve filters were still first linked mid-run, 13 ms of a
  36 ms frame on the first enemy death. `scene/filterWarmup.ts` draws one 4x4 probe per actor filter
  behind a covered frame, once per session. After it, no program was linked in 40 s of play.

### The steady cost: a 4x-throttled CPU holds 60

Under a 4x throttle a quiet walk cost 17.1 ms of work per frame at p50 and 36–54 frames a second.
Hooking each render group's `structureDidChange` with a stack trace showed where it went. Most of
the frame was **render-group rebuilds**, not drawing:

- Every mover wrote its Y-sort key through the `zIndex` setter, which flags the group for a rebuild.
  `scene/ySort.ts` writes the key silently, and re-sorts once per frame, only on a real crossing.
- A Pixi 8.19 bug meant every changed Graphics asked for a rebuild, so a door's per-frame floor pulse
  rebuilt the root group on 72% of frames. `render/graphicsPipeFix.ts` patches it, and the door's
  three per-frame Graphics are `no-batch` and hidden while empty.
- `entities`, `fx` and `numbers` got render groups of their own, so particle churn rebuilds only
  particles.
- `world` got a `filterArea`, since without one Pixi walked every descendant for bounds each frame.
  The chromatic pass leaves the chain while it is at rest.
- Standing pieces are culled with the ground: 63 pieces stood in the Y-sorted layer, with 5 on
  screen.
- A descend's teardown and its wall planning are now two `solo` build steps. Together they had been
  the one over-budget frame of the staged build.

The design record is [design/rendering/01](../rendering/01-foundations.md) ("Steady load", at the end
of "Layers"). Filter-area, chromatic and culling changes were each pixel-identical in an A/B (0 px,
the culling at 16 camera positions).

### The guard, and the tools

Every fix above has a unit test of its own, and none of those tests can see the NEXT fixture that
sets `zIndex` per frame or leaves a per-frame Graphics batchable. The guard below is what can.

**`client/src/game/controllers/steadyFrame.test.ts`** drives the real `GameLoop` over a real level-1
run, with the shipped `Scene`, `RoomBuilder` and `FxController`. After each frame it runs Pixi's
render-group upkeep without a GPU, using Pixi's own pieces: `runOnRender`, `validateRenderables`
against the real `GraphicsPipe`, and `updateRenderGroupTransforms`. It asserts four things:

- an idle second rebuilds nothing but the dust layer;
- walking and a real fight rebuild only where the tree really changed;
- a tree change is never missed;
- the root never rebuilds.

**Mutation battery: 8 of 8 source mutations killed.** The mutations were:

- the setter put back;
- the pipe fix not imported;
- the pulse batchable again;
- each of the three render groups removed;
- the Y-sort flagging every frame;
- the Y-sort never flagging.

Two traps in the harness, both found by the battery:

- The test must not import `graphicsPipeFix`. The import installs the patch, so it masks a scene
  that stopped importing it.
- A rebuild must clear `didViewUpdate` across the subtree. A new Graphics starts with the flag set
  and would otherwise never report a redraw.

**`client/tools/perf/`** holds the two live measurements, moved out of a scratchpad:

- `npm run perf:accept`: the 60 s acceptance run on a throttled CPU, with a descend halfway.
- `npm run perf:cull-ab`: the culling pixel A/B, with three controls — determinism, the camera
  moving, and the diff being able to see a piece at all.

Its README records the setup, including the Chrome flags without which a covered window draws no
frames, and the numbers to compare against.

### Numbers

- **4x throttle, dev build, 60 s with a descend at 30 s:** 59–61 frames every second, spread 2, work
  p50 6.1 ms, p99 15.6 ms. Before: 36–54, p50 17.1 ms.
- **Unthrottled:** 59–61, work p50 1.5 ms (was 2.5).
- **Client suite:** 7,937 tests green, coverage 98.42/94.84.

### Still open

- **The cold start.** On a freshly loaded dev page the first ~30 s at 4x run 2–3x slower while V8
  optimises. The run straight after a 30 s warm-up read spread 6 (55–61), and the next run read
  spread 2. Real, but a property of the page load. It has not been measured on a production build or
  on a real device.
- **No real phone yet.** A 4x throttle models a slower CPU, not a phone GPU or its resolution
  multiplier, and this pass cut CPU cost almost exclusively. If a phone is GPU-bound — the light
  pass, the stand pass's MSAA, the floor's overdraw — none of this helps it.
- **This machine is shared**, and a 4x throttle multiplies whatever else runs. The README's noise
  section says how to read a red run.
