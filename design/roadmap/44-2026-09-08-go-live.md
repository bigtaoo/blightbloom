# 2026-09-08 — going live: the backup that never ran, and the guest that was a broken SDK

Volume 44, the launch-readiness queue's last engineering volume before submission. One
instruction — *"现在要做的是把它推上线并提审"* — with a five-step order attached, of which two steps
are irreducibly the owner's (registering the developer account, asking the platform a question).
What the other three found is the shape of this volume: **both things that went wrong were
things a green pipeline was already reporting as fine.**

## The backup that never ran, and the check that existed only in the repo (2026-09-08, server + deploy + CI + docs, no engine change)

The instruction came with a correct instinct and the wrong reason for it: *"这是本项目第一次在有真实
数据的机器上改 schema…**先手动打一份 accounts.db / billing.db 快照**，别赌每日备份的时点"* — take a
manual snapshot rather than trusting the daily backup's timing.

Both halves of that turned out to be false, in opposite directions.

### The premise: there were no real rows

The snapshot was taken first, correctly — `VACUUM INTO` through a read-only handle rather than a
`cp` of a live file, which can tear — and it verified clean: `integrity_check ok`, and `accounts`
carrying no `display_name`, i.e. genuinely pre-migration.

It also showed **0 rows in every table of both databases.** Not a small number: zero accounts,
zero sessions, zero ratings, zero meta_state, zero entitlements, and zero of all six billing
tables. The backend has been live since 2026-09-07 and nobody has registered.

So volume 43's note — "the first deploy of this project that changes a schema on a box holding
real rows" — described a risk that did not exist yet. The migration then applied exactly as
designed (`display_name TEXT`, nullable, no default, `PRAGMA table_info` guard, `integrity_check
ok` after). The generalisable part is the one worth writing down: **a green migration over an
empty table is not evidence about the same migration over a full one.** Count the rows before
calling a migration production-proven. This one still isn't.

### The real finding: 18 hours of zero backups, with CI green

The daily backup worker that landed in volume 42 had, at the moment of this deploy, **never
produced a single snapshot.** `~/wnet-test/backups` was empty and the container had been in a
restart loop for 18 hours. Two independent faults, and the reason both are recorded is that
**either one alone would have been caught by the other.**

**Fault 1 — a bind mount hides the image's `chown`, silently.** `server/Dockerfile` does
`mkdir -p /data /backups && chown -R node:node /data /backups`, and for a bind-mounted path that
is useless: Docker creates a *missing* bind-mount source as `root:root` on the host, and the
mount then REPLACES the image's directory — ownership included. `backups/` was created
root-owned by the very deploy that introduced the worker, the container user (uid 1000 = `node`)
could not write to it, and every cycle died `EACCES` on `/backups/status.json.part`. The
container going unhealthy and restarting is `--health`'s staleness arm working exactly as
volume 42 designed it. Nobody was looking.

Why `./data/matchsvc` works and `./backups` did not is worth knowing for the next mount on this
box: the data dirs happen to be uid-1000-owned already, because container `node` (1000) is host
`elkadmin` (1000) here — while the account CI and a human log in as, `tao`, is 1001. So `id` on
both sides before assuming a mount is writable; the coincidence is doing the work.

**Fault 2 — the guard that would have caught fault 1 existed only in the repo.**
`deploy/ci-deploy.sh` grew a backup-health poll in the *same commit* as the worker — the one
thing that would have failed that deploy instead of shipping a dead service. But the LIVE copy of
that script is hand-installed on purpose (§6: the CI key must not be able to rewrite its own
forced command), and it never was. The deploy therefore ran the previous script: no
`dist/backup.mjs` in the payload check, no backup verification at all, **green in 46 seconds.**

That old script's own surviving comment, still on the box, read: *"a silently failed deploy is
exactly as bad as a silently failed backup."*

This is the more transferable of the two. **For any file whose live copy is deliberately not
deployable, editing the repo copy does nothing, and CI going green is not evidence that the new
check ran.** The standing answer is a diff, now in `deploy/README.md`:

```bash
ssh wnet-server 'cat ~/wnet-test-ci-deploy.sh' | diff - server/deploy/ci-deploy.sh && echo IN-SYNC
```

### What shipped

Fault 1 is fixed by construction rather than by hand: `ci-deploy.sh` now normalises the ownership
of every bind-mounted state dir before `compose up`, and it is idempotent by shape — it `stat`s
first and only starts a container for a dir that is actually wrong, so the steady state costs
three `stat` calls and starts nothing. The chown itself has to go through a root container
because `tao` has no `sudo` on this box:
`docker run --rm -v <dir>:/fix --entrypoint chown alpine:latest -R 1000:1000 /fix`.

`deploy.manifests.test.ts` gained the guard that keeps it fixed. Its hand-rolled compose reader
now parses `volumes:` too, and the new assertion pins the deploy script's chown list to
compose's **real** bind mounts — so a service added with a new mount and no chown reintroduces
precisely the original bug and fails in CI instead. It also asserts the literal `1000:1000`
against the Dockerfile's `USER node`, because a uid written as a number in a shell script is only
correct while the image still runs as that user, and leaving that a coincidence is how it breaks.
Both assertions were verified against mutants (dropping `backups` from the list; changing the
uid) before being trusted.

Fault 2 has no code fix available — that is the whole point of the hand-install — so it got the
diff recipe above, the incident written into `deploy/README.md` as a blockquote under the section
that claimed the verification was part of the deploy (true of the repo, not of the box), and the
current script installed. The next deploy's log carries `wnet-test-backup health ok`, which is
the first time that line has ever appeared.

### The go-live verification, and the control it needed

Deployed, then verified from outside rather than by reading code:

| Check | Result |
| --- | --- |
| `accounts.display_name` | `TEXT`, nullable, no default, `integrity_check ok` |
| `POST /auth/portal` | live — 401 `invalid portal token` on junk, **not 404** |
| `DDU_CG_GAME_ID` warning | fires exactly once at boot, as designed |
| `/find` + `Authorization: Bearer` | ticket payload carries `"name":"smoketest_0908"` |
| `/find` with **no** header | ticket has **no `name` field at all** |
| body `accountId` + Bearer | body value ignored, session wins |
| `wnet-test-backup` | healthy through three deploy cycles, six real snapshots |

The middle three are the point. A ticket containing a name proves nothing on its own — the
discriminating facts are that a request *without* the header produces a ticket with no `name`
key, and that a body-supplied `accountId` is discarded when a session is present. That last one
is the trust boundary volume 43 built: a name is the one field other players see, so a
self-declared one is an impersonation primitive. **A smoke test with no control is not a
measurement**, and this is the same lesson the balance sims keep teaching in a different costume.

The throwaway account was then deleted (all tables back to 0) and its token confirmed to no
longer authenticate — the deployed `accounts.db` is empty and should stay that way.

`DDU_CG_GAME_ID` remains unset, which is still correct: until the platform assigns an id,
`/auth/portal` accepts a user token minted for any game there. The `.env` plumbing was proven
with a placeholder (the process reads it; the startup warning disappears) and then **reverted**,
because a placeholder is worse than absent — it rejects every real token and looks exactly like a
broken integration.

## A hosted policy, and the guest that was really a broken SDK (2026-09-08, client + docs, no engine change)

Two of design/20's named gaps, closed — and one of them was closed twice, because the first
version of the fix was wrong in a way the module's own docstring admitted.

### The documents

`client/public/{privacy,terms}.html`, live at `b.gamestao.com/privacy` and `/terms`. The
in-game data notice already covered the point of collection; a portal wants the document too.

Entity facts came from the sibling `funny` project's pages (Tao Wang, independent sole trader,
Germany, `support@gamestao.com`), but the **content is written from what this game does rather
than adapted**, because the two differ in ways a copied policy would misstate — and a privacy
policy that overstates collection is as wrong as one that understates it:

- **no email address is collected anywhere.** Registration is username + password only; the
  schema has no email column and never had one.
- **no analytics or telemetry exists in the tree at all.** Verified rather than assumed — the
  grep that looked for it matched only the audio term *amplitude*.
- **no payment processor is connected.** Verified against the live deployment, not the config:
  `/webhook/dev` answers 404 (billsvc is never proxied through Caddy) and `/store/skus` answers
  401, so the dev stub cannot settle an order or mint a free entitlement from outside.
- **ads are portal-only and player-initiated**, served by the portal, and we receive no
  advertising identifier — only whether the ad finished.
- **an account is optional**, so a guest's data never leaves the browser. That is the strongest
  thing either document has to say, and it now leads the privacy page instead of appearing in a
  retention clause.

The three `localStorage` keys are named in full, including the fact that they carry the project's
old working name — a policy that tells a reader how to clear their own data should name the keys.

### The rule that outlived the gap

design/20's entry read: *"Nothing renders a link until one exists — an empty placeholder link is
worse than none."* That rule survives the URL existing, so it moved from prose into a type:
`policyUrl()` in `platform/policyLinks.ts` returns `string | null` and a screen has to handle the
null.

The first version of that module was decoration. Its null arm was unreachable — the URLs are
non-blank constants, so nothing could produce a null, and the guard in `MainMenu` could never
fire. That is a coverage hole and a design smell arriving together, and the second version fixed
both by making the guard do real work: `isUsablePolicyUrl` refuses anything that is not absolute
`http(s)`, and the table is injectable so the absent case is reachable from a test.

The predicate is not defensive generality. **A relative `/privacy` is this target's specific
trap**: it works on our own domain and resolves against the *portal's* host inside an embedded
frame, so it would 404 for exactly the players the link is required for while passing every check
run on `b.gamestao.com`. The same dependency runs the other way through Cloudflare —
`wrangler/client.jsonc` now states `html_handling` explicitly, because the clean `/privacy` URL
those links use rides on it and would fail silently if it changed. Verified live: `/privacy` and
`/terms` answer 200, and the `.html` and trailing-slash forms 307 to them.

The link renders under the notice it belongs to on `MainMenu` (portal) and `LoginScreen` (every
other target). Its position is a fixed offset rather than `notice.height`, which is how the rest
of both files already works: reading `.height` on a Pixi `Text` forces a canvas text measurement,
and these screens are unit-tested with no `document` — the first version broke 27 tests learning
that.

### `getUser BROKEN`: the state the instrument could not report

The instruction's step 5 said to watch `__portal.diagnostics()` on the real domain, and named the
state to look for: *"最该看的是 `NOT signed in (<reason>)` —— 平台说这个玩家登录了而我们没拿到
session"*.

**That arm cannot fire for the risk step 4 is about.** `readUser` goes through `settle()`, and
that function's documented contract is that a failure is *indistinguishable* from a call that
legitimately returned nothing — "and that is the point: no caller branches on it." So a `getUser`
that threw produced a null user and printed **`guest`**, with `lastError` still null: identical
to a player who simply is not signed in. `NOT signed in` only fires when a portal user WAS read
and our own exchange then failed.

Which means the one instrument this repository has for the half of the integration it cannot test
was blind precisely where the danger is. `getUser` is in BETA on the platform's side — the SDK
logs it on every call — so "it does not work" is the likeliest failure of the entire silent-login
path, and it would have looked like a quiet day with no logged-in players.

Fixed without reopening what `settle` closes, which is the constraint that shaped the fix:

- `settleReporting` keeps the reason. `settle` now delegates to it, so there is one try/catch
  rather than two copies that can drift, and a test asserts the two never disagree.
- `readUserReporting` also treats an **un-narrowable** answer as a failure rather than as a
  guest. That is the renamed-field case, and it is live: the platform has already removed one
  field from this object, so an answer we cannot read is a real outcome and calling it "guest"
  would hide exactly the breakage worth knowing about. A *missing method*, by contrast, stays a
  failure-free guest — that is `auth unavailable` upstream, not a broken read.
- `PortalSession.diagnostics()` reports a fifth state, `getUser BROKEN (<reason>)`, **checked
  before the guest arm** — the two share a null user, so a guard placed after it would be
  unreachable through the public surface. A test pins the order rather than only the wording.
- A boot-time failure clears when the auth listener later delivers a real user, or the instrument
  would keep accusing a working SDK for the rest of the session.

Nothing branches on the flag to decide what the *game* does. Every failure path still ends at a
fully playable guest, which is the rule `settle` exists to enforce; only the diagnostics line
changes. `settle`'s own docstring now says where the line is, so the next person to want a reason
finds the sanctioned way to get one instead of relaxing the invariant.

### Two corrections to what is verifiable off-host

- **`isUserAccountAvailable` is already `true` on the unregistered `local` domain** — measured,
  `{available: true, portalUser: null, session: null}`. So "check whether it is true on the real
  domain" proves nothing; it is true here too. The discriminating signal is `portalUser`
  *populating*.
- **The sub-path serve is finally runnable.** `launch.json` had carried a note since the target
  landed saying its dev config serves from the ROOT and therefore cannot prove the thing this
  build is most likely to get wrong — and the config to actually run that check did not exist.
  `client-crazygames-subpath` is `vite preview client --outDir dist-crazygames --base
  /games/blightbloom/`, no copying required. The real assertion is not a screenshot but
  `performance.getEntriesByType('resource')`: **82 same-origin requests, 0 failures, and nothing
  requested from outside the sub-path.** An absolute path leaking is the failure, and it is
  invisible when served from the root.

**Tests: client 5434 → 5475 (two new files), server 1175 → 1176.** `npm run check` clean,
`tsc --noEmit` clean, coverage green on the 90/90 gate over the full tree (client 97.54% lines /
92.86% branches, scope 253/253 — engine and server unchanged and green). Every new assertion in
this volume was verified against a mutant before being trusted, and one apparent survivor turned
out to be a no-op edit — a reminder that a mutation that did not apply reads exactly like a test
that does not bite.
