# 2026-09-08 — the codename's last surface: `DDU_*` becomes `BB_*`

Volume 45, a naming pass with an operations tail. One instruction — *"DDU_CG_GAME_ID 游戏里还有
很多类似的DDU开头的命名，现在游戏有自己的名字了，改为BB开头的吧"* — pointing at the one family of
identifiers the 2026-09-06 rename (volume 39) deliberately left on the codename, and the reason
this is a volume rather than a `sed` is that **the binding for these names lives in a file CI is
forbidden to ship.**

## The codename's last surface (2026-09-08, server + deploy + docs, no engine change)

Volume 39 renamed the game and held the code change to one line: **a name a human READS moves, an
identifier a machine MATCHES does not.** It then listed what did not move and why — `daydayup.*`
localStorage keys (renaming them wipes every player's save), `REPLAY_FILE_KIND` (matched against
bytes on disk), the `daydayup-*` Worker names (a renamed Worker is a *new* Worker), `de.elk.daydayup`
(a changed bundle id is a new app). The `DDU_*` environment prefix was not on either list, which is
its own small finding: it is machine-matched, so it did not qualify to move, and it is the only
machine-matched name in the tree whose match is **re-bindable at zero cost** — the other side of the
match is one file an operator owns, and rebinding it loses nothing and breaks no artifact anybody
already holds. That is a third category, and it is why this rename is possible at all.

**22 names, 66 files, 314 lines, line for line.** `BB_TICKET_SECRET`, `BB_INTERNAL_KEY`, `BB_DB_PATH`,
`BB_BILLING_DB_PATH`, `BB_BILLING_DEV_STUB`, `BB_BILLING_DEV_ORDERS`, `BB_MATCHSVC_URL`,
`BB_GAMESERVER_URL`, `BB_BILLSVC_URL`, `BB_CG_GAME_ID`, `BB_BACKUP_{DIR,INTERVAL_HOURS,KEEP}`,
`BB_GRANT_AUDIT_THRESHOLD` and the six IAP-provider credentials, across `src/`, `test/`, the
Dockerfile, `docker-compose.yml`, `.env.example`, both READMEs and every design doc and roadmap
volume that cites one. No behaviour moved with them: `tsc --noEmit` clean, `npm run check` green,
**9066 tests across all eight workspace packages**, none added and none removed.

**The gate that made this a `sed` instead of an audit — and the way it depends on the string being
renamed.** `deploy.manifests.test.ts` cross-checks the compose file against the source: every env
name set in `docker-compose.yml` must be read somewhere under `src/`, so renaming either side alone
is red before a deploy exists. Worth writing down is that the checker's own scan is
**prefix-literal** — one of its three patterns is `/'(BB_[A-Z0-9_]+)'/`, there because
`startupGuard`'s `DEV_ONLY_FLAGS` reaches its names through `env[name]` and no `process.env.X`
pattern can see them. A gate whose implementation hardcodes the string under rename is exactly the
shape that goes quietly blind; this one happens to fail SAFE (a stale pattern drops
`BB_BILLING_DEV_STUB` out of the known set, and compose's copy of it then fails the "read nowhere in
`src/`" assertion), but that is a property of this checker, not of the shape.

**The whole risk is two lines in a file CI cannot touch.** `ci-deploy.sh` ships `dist/`, the
Dockerfile and `docker-compose.yml` and deliberately never `.env` — the ticket secret and the
internal key live only on the box, and that is what bounds the deploy key. Every other renamed name
is set in compose, i.e. rides the deploy. These two do not, and **the two failures are asymmetric in
exactly the wrong direction**: an unset `BB_INTERNAL_KEY` under `NODE_ENV=production` fails CLOSED
(rating reports and the store proxy start being refused, loudly, by design), while an unset
`BB_TICKET_SECRET` falls back to the **published dev secret** with a one-line warning and everything
keeps working — a live-server security downgrade whose only symptom is that it looks healthy. The
quieter failure is the more dangerous one, which is the argument for doing the `.env` edit *before*
the merge rather than after the alarm.

**Ordering, and why there is no window.** `env_file` injects names, not a schema, so a `.env`
carrying BOTH prefixes is read correctly by the old code and the new. The migration is therefore
additive-then-subtractive rather than a swap: duplicate the two lines under the new prefix now, merge,
let the deploy land and `/health` answer, then delete the old lines. Written out with both commands
in `server/deploy/README.md` §Secrets, because it is the kind of step that is obvious for about a
week.

**What did not move, now with a comment saying so.** The map editor's three autosave keys
(`ddu-mapeditor:arena|dungeonFloor|room:*`) stay on the codename for volume 39's own reason — they are
matched against a key already sitting in a designer's browser, so renaming them silently drops an
unsaved draft rather than renaming anything, and no human reads them. All three now carry the
one-paragraph why at the declaration, the same treatment volume 39 gave `REPLAY_FILE_KIND`, so the
next sweep does not "finish the job". The `bb-` change to a dozen `mkdtempSync` prefixes in the server
tests is the opposite case and went with the rename: nothing matches those strings, they only appear
in a path a human reads while debugging.

**Still open, and not closable from inside this repo:** the live `~/wnet-test/.env` still holds the
two `DDU_*` lines — one SSH command, in the README. `BB_CG_GAME_ID` also remains unset on the deployed
matchsvc, unchanged by this pass: the id does not exist until the portal assigns one, and volume 44's
`/auth/portal` warning is still the thing that will say so. `platform` `docs`
