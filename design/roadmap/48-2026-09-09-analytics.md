## Retention, and the sentence a policy stopped being able to say (2026-09-09, client + server + deploy + docs, no engine change)

*"funny的后台管理系统，我们这边应该也需要，只是不需要那么多功能。主要的用户管理和留存打点肯定是要的，你看看还有其他功能对我们有用吗"* — then *"隐私政策改说明。暴露到公网。先文档再按顺序实现"*, then *"继续，直到做完为止"*.

The ask was `funny`'s ops backend: `server/admin` (5,285 lines) plus `tools/ops` (6,756).
Almost none of it is here, and the reason it is not is worth more than the part that is.

### Two things already in place shrank the problem to a third of itself

**The monitoring half was already answered.** Volume 47 landed Loki/Alloy/Prometheus/Grafana
the same morning. `funny`'s `monitorRoutes` and its ops "Monitor" page exist to show online
counts, queue depth and trends; `server/src/metrics.ts` already exports those and Grafana
already graphs them. Nothing here re-implements it.

**Grafana IS an ops frontend**, deployed at `https://bb.gamestao.com/grafana/` behind its own
login, with users, permissions, provisioned datasources and reviewed dashboards. `funny`
hand-wrote 6,756 lines of frontend because it had no such thing in front of the same data.
Re-enacting that here would be building a worse Grafana. So the scoping rule for the whole
document became: **anything expressible as a time series goes to Prometheus and is drawn by
Grafana; a bespoke page is only justified for what a time series cannot express.** Exactly one
thing qualifies — a row per player — and that is all of `funny`'s admin that survives.

[`design/21-ops-analytics.md`](../21-ops-analytics.md) is the plan: eleven locked decisions,
three phases, and a table of the eight `funny` capabilities deliberately not adopted with the
reason for each. **Phase A shipped in this pass. B (the read-only console) and C (feature
flags) are designed and not built.**

### The decision that makes a publicly exposed console proportionate

The owner asked for it on the public internet, which raises the bar rather than lowering it.
The answer is B2: **the console is read-only over player data, and every player-data mutation
— password reset, ban, entitlement grant — stays a CLI script run on the box.** SSH access is
the second factor, and it is one we already have and already protect. The worst outcome of a
total compromise is disclosure, not modification.

That single decision deletes RBAC, the four-role capability matrix, the compensation approval
workflow and the audit-visibility split from scope — which is the largest block of `funny`'s
admin. There are no writes to gate. B1 makes it structural rather than a rule: `adminsvc` will
open every database with `readOnly: true`, so "cannot write player data" is a sentence that
survives a bug in it. It also supersedes design/19 §7's *"No admin service... Revisit when the
first refund arrives"* — and not by the trigger it named. The reason is retention measurement
and operability, not refunds; §7's actual requirement (the schema must be hand-correctable
with SQL) survives intact, and B2 depends on it.

### Phase A: what was built

One shared vocabulary (`client/src/net/analyticsEvents.ts`) imported by the client that sends
and, through `@dd/net/*`, by the server that refuses everything else — literally the same
module, because two copies that drift produce no type error and no red test, only an event
sent forever and dropped forever. `POST /client/events` is a sibling of `POST /client/log` in
the same file, sharing its limiter, its IP key and its always-200 contract; a third SQLite
database (`analytics.db`) with three tables; an hourly rollup job whose gauges land on
matchsvc's existing `/metrics`; a Grafana dashboard; and the client SDK plus the derived
events.

Four decisions inside that are load-bearing:

- **`daily_active(day, install)` is a separate table from `events`, and keyed to make DAU a
  partition.** A cohort query never scans `events`, so retention does not DEPEND on the prune
  — otherwise the day the events window drops its oldest week, D7 for that week silently
  becomes `0` rather than unknown. And an install that plays on two hosts in a day gets one
  row, so DAU-by-host sums to exactly DAU instead of double-counting a switcher.
- **The rollup writes before it exposes.** Prometheus keeps 15 days and a gauge cannot be
  backfilled, so a chart built only on scrapes silently begins two weeks ago however long the
  game has been live. `daily_rollup` is the record; the gauges are a view, and the dashboard
  has a panel that says so.
- **An unaged cohort is absent, never zero.** `cohortRate` returns `null` both for a cohort
  that does not exist and for one whose offset day has not finished, and the gauge is SKIPPED
  rather than emitted as 0. A gauge has no "unknown", so absence is the only way to say it —
  and it matters most in the first week after launch, when every offset is unaged and a zero
  would read as "nobody ever came back".
- **Collection is opt-in by env var with no default path.** `BB_ANALYTICS_DB_PATH` unset means
  the route still answers 200 and stores nothing. The same name is what the backup worker
  discovers the file by, so "collected" and "backed up" are one condition instead of two that
  can disagree.

**The install id turned out to already exist.** The plan called for a new `install_id`;
`net/identity.ts` has stored a random UUID at `daydayup.playerId.v1` since the PvP squad work,
with a storage port and a non-`crypto` fallback. Reusing it means analytics adds no new stored
identifier, existing players keep the id they have (so retention is continuous from the day it
ships rather than starting at zero), and there is one fewer thing for somebody clearing site
data to find. What it could NOT reuse is `getPlayerId()` itself, which prefers the account id
once a session exists — right for a ladder key, wrong for a cohort, because a player who logs
in halfway through their second visit would change identity mid-cohort and read as one install
that vanished plus one that appeared. `getInstallId()` sits beside it and never prefers the
account; the two disagree on purpose and each has the test that fails when they are confused.

**Three events are derived from the frame rather than announced.** `screen_view`, `run_start`
and the abandon half of `run_end` come from one per-frame comparison called from
`GameLoop.update` — the same argument `powerBudget.ts` makes from the same call site.
`RunState.phase` is written in fifteen places; a `track()` in each would be fifteen chances to
forget one, and the forgotten one reads as a funnel step that is merely unpopular. It also
means **abandonment is detected, not reported**, so a quit route nobody thought of is still
counted. Screen ids are an explicit exhaustive table, not a case conversion: the server's id
charset would REFUSE `modeSelect`, and that step would silently never appear.

Two vocabulary entries came back out, both for the same reason — a declared field nothing can
populate is an always-empty column and an always-empty panel. **`run_start.weapon`**: no
authored weapon id survives into the sim state (a `WeaponState` carries the numbers the sim
reads; an actor keeps `atlasKey` because something has to draw it). **`store_open`**: opening
the store IS a `screen_view`, and the rollup counts those per screen, so the conversion
denominator already existed.

### The privacy policy could no longer say what it said

`b.gamestao.com/privacy`, written 2026-09-08, said *"No gameplay analytics or telemetry. The
game does not report your play sessions, events, or behaviour to us."* Volume 47's client log
shipping had already put that in tension; Phase A falsifies it. P1 is the rule that the rewrite
ships in the same pass as the instrumentation, not after — shipping collection against a live
policy that denies it is the specific failure the ordering exists to prevent.

**The bullet was not the real problem; the callout at the top was.** *"Playing without an
account collects nothing on our server"* is the sentence a reader acts on, and it is exactly
false for analytics, because a guest is *who retention is about*. It now names the two things
sent without an account and points at the section describing them.

**And the localStorage list was already wrong before any of this.** It said "there are three
items" and named three, while the shipped game has been writing `daydayup.playerId.v1` as a
fourth all along — a disclosure gap independent of anything designed here, and the reason the
rewrite was the right place to fix it rather than a follow-up. Every number in the policy is
now a number the code deletes on: 90 days for events, 180 for the day-level cohort rows, 14
for error reports (checked against the log store's own `retention_period: 336h`, not
asserted), and no limit for day-level totals, which is honest precisely because those rows
hold no id. §9 says what a data-subject request can and cannot reach — including the honest
answer for a guest, whose records carry only an id that exists in their own browser and which
we therefore cannot look up on their behalf.

The cohort window came down from 400 days to **180** in the writing: a policy has to state the
number and the number has to be defensible. 180 is what a full three-month return curve needs;
anything past it is data kept in case a question is asked later.

Not resolved, and named as a question rather than quietly asserted: **whether an EU consent
banner is required.** Legitimate interest is stated for both new rows and reusing an existing
id means no new storage access, but ePrivacy asks about the PURPOSE of reading terminal
storage, and first-party product analytics is the contested case. The design makes either
answer cheap — `setAnalytics(null)` is already the default and already a no-op at every call
site, so a consent gate is a call site rather than a redesign.

### One host is deliberately excluded, and that is the interesting part

**Analytics is NOT installed on the WeChat entry point.** Not caution: every row is keyed by
the install id, which persists through `createWebIdentityStore` — and that reads
`localStorage`, a global that shell does not have. The availability check is false on every
boot, so a FRESH id is minted per visit. The consequence is asymmetric and that is what
decides it: retention would read 0% instead of being absent, which is bad; but **DAU would
report the number of VISITS while labelled *distinct installs***, which is worse — a plausible
number nobody would question. No data beats wrong data.

The fix is not an analytics change. `IdentityStore` is already the seam, and a
`wx.getStorageSync` implementation would fix this, the meta save (a WeChat guest's progress
does not survive a reload today either — `meta/store.ts`'s own header has called that adapter
"a later platform impl" for months) and the settings store together. The portal build IS
installed, with its weaker case stated rather than discovered: an embedded frame may have
storage blocked, so for those viewers the id is per-visit and DAU there reads slightly high.

### What RUNNING it found, which neither the tests nor the review did

Phase A's definition of done was *a real number off a real dashboard, not a merged branch*.
Driving the real dev client against a real matchsvc produced the funnel in order —
`session_start`, `screen_view{menu→mode_select→forge→playing}`,
`run_start{character: char_vanguard}`, `screen_view{paused}`, `run_end{abandon}`,
`screen_view{forge}` — plus `session_end{duration_s: 141}` from the previous visit's exit
flush and an `accepted: 3` for a four-event batch whose fourth name was not in the vocabulary.
It also found two defects.

**Every abandoned run reported no floor and no duration.** Quitting to the forge tears the
engine down, so by the frame the phase change is observed `activeState()` is already `null`,
and the props were read from the CURRENT state. The event survived — a run whose floor is
unknown is still abandoned — but the one number it exists to answer, *how far did they get
before they stopped*, was missing from every row. **No test could have caught it**: at that
seam the state is an argument, and a test that passes one on the transition frame is testing a
caller that does not exist. The fix snapshots the last live run frame; four cases pin it,
including that a snapshot must not survive into the NEXT run, which would report the previous
run's floor and look entirely plausible.

**Every flush paid its own CORS preflight, including the exit one.** One `OPTIONS` per `POST`
in live traffic, because `routes/http.ts`'s shared CORS block set no
`access-control-max-age`. This is the one request that cannot be retried: the telemetry routes
flush on `pagehide`, `keepalive` protects a request the page has already STARTED, and an
uncached preflight makes the exit flush two sequential round trips behind an unloading
document — precisely the `session_end` half of the churn funnel, and precisely the event
`funny` lost outright to the same class of mistake. `access-control-max-age: 600` fixed it,
verified live as one preflight for three POSTs, and every other route on the server gets the
same saving for free.

**A verification note worth keeping.** In the in-app browser pane, wall time and SIMULATED
time diverge by about 300× — 59.6 s of ticker time advanced the sim by 6 ticks — because the
pane composites in bursts and Pixi clamps a long `deltaMS`. A `duration_s` read off a
pane-driven run is therefore meaningless, and a test asserting "duration > 0" from one would
be flaky rather than wrong. It is a sharper case of the known "a hidden pane pauses rAF" trap:
the pane does not stop the clock, it starves it.

### A new gate, and why a dashboard needed one

`deploy.dashboardMetrics.test.ts`: every `bb_*` metric a Prometheus panel queries must be a
name the server actually emits. A dashboard is the one artefact whose broken state looks
exactly like its working state — a panel querying `bb_dau_total` when the server emits
`bb_dau` draws an empty graph, and an empty graph is what a quiet day looks like. This project
had already paid for that once, the same day: volume 47's "errors by build version" panel was
fully populated and said nothing, because nothing could supply the field. The reverse
direction is deliberately not asserted (a metric with no panel is a fine state); the gate was
proven non-vacuous by renaming a metric and watching it fail.
