## PvE chapters: the Frost Descent, and every path learns which dungeon (2026-10-06, engine + client + server + art + sim + docs, no ENGINE_VERSION change)

> 现在我们需要规划pve的地牢章节了，现在只有一张地图。 — then, on the plan: 按推荐的来。缺失的资源，你参考standing目录的mistral生成图片的做法自己去弄

The decision and its reasons are [`design/gameplay/04-chapters.md`](../gameplay/04-chapters.md):
a chapter is a whole run, clearing one unlocks the next, the lobby picks, four are planned
(ember → frost → storm → blight) and two ship. This entry is what it took.

### What assumed one dungeon

A sweep before the plan found no "which dungeon" field anywhere outside a replay file (which
embeds the whole `EngineConfig`). Every one of these built or assumed `EMBER_DUNGEON` by name:
the offline and online config builders, `RunLifecycle`'s three run entries, `floorCount`'s
fallback, `SavedRun` and the resume path (a frost save would have been refused as stale by its
content hash), `MatchStart`, the ticket, the matchmaker's `${mode}:${playerCount}` queue key,
the party service, `MatchRoom`, the co-op fill bot, the three run analytics events and the
new-install depth queries, `MetaState.bestFloor`, the biome→element and biome→track maps, and
the boss pool.

### Engine and content

- **`engine/world/chapters.ts`** — the catalog. The chapter id IS `DungeonConfig.biomeId`;
  `chapterIdOfConfig` also checks object identity, so a fixture reusing a biome id is not taken
  for the shipped chapter. Chapter 1's entry hands out the same `EMBER_DUNGEON`/`EMBER_L1_ROOMS`
  objects as before, so the seven existing golden hashes did not move.
- **`world/dungeons/frost/`**, seeded by `tools/map-editor/scripts/deriveChapter.mjs` from
  chapter 1's tuned JSON: transposed, emberling↔frostling, the boss room naming `glacimaw`.
  `frostLevel1.test.ts` pins that it is still that transform.
- **The passability suite moved** from `emberLevel1.test.ts` into
  `engine/fixtures/floorPassability.ts` and runs over both chapters (101 frost tests). It found
  nothing to fix in the transposed floors: no door off a shared wall, no wall thinner than a
  cell, every spawn, chest, plate and shop ring reachable.
- **Glacimaw** + `enemyshardfan` (5-shard aimed ice cone). `enemies.ts` crossed 500 lines, so
  the four bosses and `BOSS_POOL` moved to `content/bosses.ts`, re-exported. `BOSS_POOL` is
  unchanged; chapter 2's boss room names its boss directly, so no per-dungeon pool field was
  needed.
- **Golden:** a new `frost-dungeon-floor1` scenario. Unlike the ember one it clears its first
  room within 1500 ticks (`door_unlocked` 1, 8 deaths).

### Balance: the authored 1.25 was a wall

`client/sim/chapterSim.sim.ts` (new, inside `npm run test:pve-sim`) measured the careful bot on
the starter kit. Runs past floor 0 over 80 seeds: chapter 1 25%; chapter 2 at base 1.0 21%; at
1.125 13%; at the authored 1.25 5%, and 0 of the 40 gated seeds. So `difficultyCurve.base` is
**1.125**, and the sim gates chapter 2 between 1/16 of seeds and 3/4 of chapter 1's count (both
1.0 and 1.25 fail). Glacimaw alone: 23% kills, 78% bot deaths, 25 s median, chilled 46% of the
fight, the same in chapter 1's room and scale; left as authored. The runtime of
`test:pve-sim` went from ~4 s to 30-60 s.

**An instrument that had measured nothing since 2026-09-14.** Chapter 1's entrance
reaction-time gate read "the first floor-0 room sorted by id", which since the side rooms landed
has been the enemy-free `b1_cache`, so it passed while checking nothing; the entrance-clear gate
accepted any floor-0 room. Both now read the room each run actually spawned in, and both still
pass (93 ticks of reaction; 40/40 cleared).

### Client

- **Meta:** `MetaState.selectedChapter` and `clearedChapters`; `meta/chapterProgress.ts`
  (`isChapterUnlocked`, `recordChapterCleared`, `selectChapter`, `playableChapter`). Store
  migration defaults old saves; guest merge unions clears. A clear is recorded on a PvE victory
  (`RunState.settleOutcome`), offline or online. **A first clear moves the pick to the chapter it
  unlocks**, so the unlock is visible in the lobby; a repeat clear leaves a deliberate replay
  pick alone. `selectChapter` refuses a locked chapter; `playableChapter` falls back to chapter 1
  for a hand-edited save.
- **Runs and saves:** `buildDungeonRunConfig` takes the chapter; `SavedRun.chapterId` (absent =
  ember, unknown = refused); one `rebuildSavedRunConfig` serves both "is it resumable" and the
  resume itself, so they cannot drift.
- **Lobby:** `ui/ChapterPicker.ts`, one row under SOLO: `‹` [chapter banner] `›`. Showing a
  locked chapter is not choosing it: SOLO and CO-OP dim and stop taking taps until the player
  cycles back (CO-OP too, because its queue plays the picked chapter). Checked live at desktop
  size: ember shown, frost locked with "Clear chapter 1 to unlock", and with frost unlocked a
  SOLO run built `biomeId: 'frost'` with the ice swatches and frost-tinted critters.
- **Theme/music/i18n:** `frost → ice`; frost borrowed chapter 1's dungeon track (its own since the
  music entry below); chapter names
  in all 8 locales (zh 余烬深渊 / 霜寒深渊).

### Online and server

- `MatchStart.chapterId`, optional; every co-op room now sends it, PvP never does. The client
  builds chapter 1 for absent or unknown.
- `/find` and `/party/start` read the chapter through `server/src/chapterField.ts`: absent means
  chapter 1 (every older client); present but unknown is **400 `unknown chapter`**, not a silent
  default, because a silent default would seat a player in a chapter they did not pick and
  credit the wrong unlock.
- The chapter is signed into the co-op ticket; the gameserver refuses (4403) a joiner whose
  chapter differs from the room's. Each chapter has its own co-op queue. A party carries its
  host's chapter; members' own picks are ignored. Fill bots copy the room's chapter.
- The client feeds the lobby's playable chapter to the solo co-op queue (`OnlineMatch.connect`)
  and the party start (`PartyScreen.chapterOf`).

### Analytics

`run_start`, `floor_reached` and `run_end` carry `chapter`, derived from the run's config (so a
co-op guest records the host's). First-day new-install depth counts chapter-1 runs only, since
floor numbers are per chapter; absent counts as chapter 1. `privacy.html` lists the field.

### Art

The run needed none: every boss and critter is a tinted shared rig, and the ice swatches had
shipped on 2026-08-02 with no dungeon to map to them. The two lobby banners,
`ui/chapter_{ember,frost}.jpg` (768x256, 34 and 39 kB), are image edits of the DESCEND card's raw
through `D:/standing/tools/edit_image.sh` (Mistral), so they stay one family with the route
cards. Prompts and rejections: `art/ui/prompts.md`, "Chapter banners".

### Not done, on purpose

- **The locked-door leaf stays red** in the frost chapter. It is the shared "locked" hazard
  signal, the same in every biome, not fire art. If it reads as lava in an ice level in play, a
  per-element leaf is a drop-in.
- `SettledMatch` and the integrity report do not record the chapter, and need not: both of
  their consumers (the ladder report and `buildIntegrityReportBody`) return early unless the
  room's mode is `pvp`, and PvP has no chapter. A field there would be read by nothing.
- Chapters 3 and 4 and hand-authored frost layouts: `gameplay/04` "Next". (Chapter music was
  listed here as a Suno pass only the owner could run; the owner rejected AI music instead, and
  the entry below shipped open-licensed beds for both chapters.)

### Follow-up the same day: a clear-only guest kept its unlock

A guest whose only progress was a chapter clear (the carry-out already spent at the Forge) lost
it on a first login into an account that held anything: `hasGuestProgress` counts bank,
blueprints and characters, so `resolveAccountMeta` took the account's state and chapter 2 was
locked again, silently. `guestAddsChapterClears(guest, account)` now sends that case down the
same path as an empty account: merge without a prompt (the prompt has no number for a clear),
claim the device. A guest with a bank AND a clear is still asked, as before. On a shared
computer the worst this hands another player is a chapter opened a run early.

## Open-licensed music replaces the AI loops, and each chapter gets its own bed (2026-10-06, client + assets + tools + docs, no ENGINE_VERSION change)

> 音乐我发现ai生成的并不好，你去搜索一下是否有合适的开源的吧 — then, on the shortlist: 我对音乐没什么感觉，你直接定吧。继续

The two Suno loops (`menu`, `boss`) were judged not good enough, and chapter 1's run bed had never
had a file of its own (it borrowed `menu.mp3` since 2026-08-31) while chapter 2 borrowed chapter
1's. Four open-licensed loops now ship, one per slot, including a new `dungeon.frost` track:

| track | music | licence | loop | seam |
|---|---|---|---|---|
| `menu` | "Aurora", Scott Buckley | CC-BY 4.0 | 85.0 s | 0.83 dB |
| `dungeon.ember` | "Lava Area Theme", Wolfgang_ | CC-BY 4.0 | 60.0 s | 1.54 dB |
| `dungeon.frost` | "Beyond the Frozen Veil", Synth-thetic | CC0 | 71.5 s | 1.40 dB |
| `boss` | "Colossal Boss Battle Theme" (no vocals), Matthew Pablo | CC-BY 3.0 | 58.5 s | 1.31 dB |

2.46 MB together (the WeChat check counts the `music` pack at 2.34 MB of its 3 MB).

### How it was chosen without anyone listening

The owner delegated the pick, and I cannot hear. So: a licence filter (CC0 or CC-BY; NC fails on
ads, ND on cutting a loop), then twelve candidate files downloaded and measured with the existing
pipeline (seam search on the same measure as the gate, band balance, level spread, L/R
correlation). Taste entered only as the tiebreaker, and is labelled as such in
`art/audio/README.md`. Three findings decided picks:

- **A near-perfect seam is the piece repeating.** "Ice Cave" offered 0.06 dB at 42 s and "Lava
  Area Theme" 0.21 dB at 40.5 s: head and tail were the same bars. The player's equal-power
  crossfade swells up to 3 dB and combs on correlated material, so the 1-2 dB regions of
  different material (the case the player was built and measured for) were taken instead.
- **An anti-correlated mix cancels on a phone.** "The Frigid Seas" read L/R -0.64 and was
  dropped for that alone.
- **The gate's 90 s ceiling** cut `menu` from a measured 105 s region to 85 s.

### What changed besides the files

- **The in-game credit.** CC-BY requires one, and nothing in the game had ever needed one. The
  Settings sheet now closes with a full-width music credit (`audio/musicCredits.ts`), plain text
  because WeChat cannot follow a link; checked at 800x600 and on a 375x812 phone.
  `musicAssets.test.ts` holds each line, title, author and licence equal to the `credits.json`
  record, and checks the licence against the allow-list.
- **Provenance.** `credits.json`'s `music` records name the upstream URL and SHA-256 (and the
  member file inside a 7z/zip), a captured licence statement per track
  (`art/audio/licenses/music-*-LICENSE.txt`), and the archived source's own hash. The archive is
  the upstream file when small and otherwise an excerpt (region plus 5 s either side, Vorbis):
  the upstreams total ~95 MB. The Suno masters and `music_terms` are deleted. One recorded gap:
  Matthew Pablo's attribution page is offline, so his credit follows the licence's own terms.
- **Tempo became per-track.** The 2026-09-06 0.7x stretch was a request about the Suno masters;
  `process_music.py` now carries `tempo` per track, 1.0 for all four.
- **Chapter 2's bed.** `BIOME_ID_TO_TRACK.frost` is `dungeon.frost`. That also ended an
  equivalent mutant recorded since 2026-08-31 (deleting the biome lookup changed nothing while
  every biome mapped to the fallback); `musicDirector.test.ts` now pins the frost mapping instead
  of asserting its own vacuity. Live check: a frost run put `dungeon-frost.mp3` (71.5 s) on the
  second deck (read back after the unattended run had already ended in defeat, so the bed was
  fading back to `menu`), and the menu streams the new 85 s `menu.mp3`.
- **A pipeline trap:** libsndfile's Vorbis encoder overflows the stack on one large `sf.write`
  (a Windows fatal exception, exit 127 from bash with no message); writing 4096-frame blocks
  through `sf.SoundFile` works.
