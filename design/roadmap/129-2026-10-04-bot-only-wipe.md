## A run with only bots standing ends (2026-10-04, engine + client + server + tools + test + docs, ENGINE_VERSION 88)

Volumes 124 to 126 left one co-op case open: a bot left alone after its player dies. The bot
never opens the portal, so the run went on until the bot died too, with the player watching. The
co-op sim counted these runs as `stranded`. Volume 126 found that a held-back ally makes them
likelier when its revive cannot answer: 34 of 40 aggressive runs with the revive off.

### The rule

A co-op run now ends as a wipe once every person in it is dead, whatever bots are still
standing (`WinConditionSystem`, right after the "nobody up" check).

- **Dead, not downed.** A downed person is still alive, and the bot may yet revive them, so
  the run goes on. Only a bleed-out ends it.
- **Every person.** In a room of two people and a bot, the run waits for the second person.
- **People must exist.** A run with no person in it (a sim's all-bot run) is not ended by this
  rule; there is nobody to strand.
- **Co-op only.** The check sits inside the PvE branch; an arena ignores the flag.
- The ending is the ordinary wipe: `winner: 'enemies'`, one `win` event, `phase: 'gameover'`.

### What a seat being a bot means

`PlayerConfig.bot` is new and optional, and `PlayerActor.bot` carries it on the seat
(`buildSeat`), hashed in the replay state after `portalReady` (`replay.test.ts` pins that the flag alone
moves the hash). A config with no bot seat (solo,
and every config before 88) is unchanged: there every person dead is nobody up, which the check
before it already ended. The golden gate was green before the bump and moved only on schema.

Who sets it:

- **Offline co-op** (`offlineConfig.ts`): the ally seat is `bot: true`.
- **Online co-op**: the bot seats `Matchmaker.formWithBots` fills. Co-op has had bot backfill
  since 2026-09-17, so this case is reachable online as well as offline. The flag goes:
  - `matchsvc`'s `onBotFill` signs `bot: true` into each bot seat's ticket, beside the room,
    owner and seed it already signs. `verifyTicket` rejects any other value.
  - The gameserver's `resolveSeat` takes it off the verified ticket, and the connection carries
    it into `MatchRoom`, which marks the seat on join.
  - `match_start` gains `botSeats`, the bot-held seat indices. As with `names`, it is
    `undefined` in a room with no bot, so a room of people puts nothing new on the wire.
  - `buildOnlineConfig` flags those seats in co-op (PvP ignores the field). Every client and
    `BotClient` builds its engine through it, so every engine in the room agrees.
  - `conn_resync` does not carry it: no client builds an engine from a resync, only from
    `match_start`.

A client cannot claim a bot seat or shed one. The flag comes only from a signed ticket, which is
how seat names already reach the room.
