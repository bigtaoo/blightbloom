## The rewarded ad is an OFFER, and the offer is the part that was missing (2026-09-07, client + docs, no engine change)

Volume 41 landed the whole ad layer and then filed the rewarded ad as **open**, on the grounds
that "every rewarded reward in a roguelite touches balance" and that a product decision must not
be settled by an engineering pass. That was the right call and it left a precise gap: the
transport (`sdk.requestAd('rewarded')`), the policy (`AdController.rewarded`, never in gameplay,
never online, muted and frozen, released in a `finally`) and the adblock probe that decides
whether a reward may be advertised at all were **all shipped and all tested** — and nothing
anywhere called them. What was missing was not the ad. It was the **offer**.

### The decision, and the two rules it had to clear

Asked, with the three candidate rewards and their costs, the owner picked **double the
extraction payout**: watch a rewarded ad on the results screen and the run's carry-out bag is
banked a second time. `design/20`'s "The rewarded-ad placement" holds the full argument; the
short version is that it is the only candidate that clears both locked rules at once.

- `design/05`'s **wipe rule** kills every reward shaped like a continue. "Keep your materials
  after a wipe" and "watch an ad to revive" are the same violation, so the offer does not exist
  on the defeat screen — *absent*, not disabled. `RunOutcome.lose` passes no offer argument at
  all, and the test asserts `undefined` rather than `null` specifically so that a later pass
  cannot wire one in and merely grey it out without turning a case red.
- `design/14`'s **"sell breadth, not power"** picks the currency. A material is not power: it is
  the farmable half of the economy and it is spendable only on blueprints the account already
  owns. An ad that granted a run buff, a revive or a weapon would sell power for attention,
  which is the axis the monetisation model refuses to sell for money. That rule is now written
  into `design/14` itself, as a bullet, because "an ad may not sell what money may not" is a
  monetisation constraint and it was only inferrable from two documents before.

### The ordering is the guarantee, not a second code path

The requirements page asks that a player who does not watch the ad be left with the non-ad
alternative rather than nothing. The way to get that wrong is to compute the payout, hold it, and
grant it after the ad resolves — which reads as equivalent and makes an unfilled request, an
adblocked player and a mis-timed screen close indistinguishable from a wipe.

So the baseline bag is banked **before** the offer is drawn, and the reward is literally the same
bag banked a second time (`bankRunMaterials(s)` twice, with the same state). A player who ignores
the button keeps 100%. `RunOutcome.test.ts` asserts on `banked` for every case, because that array
is the only observable that can tell the two orderings apart: the lines on screen look the same
either way.

### Four reasons there is no offer, and where they live

No rewarded ad installed (every target but the portal), the player blocks ads, the run was
ONLINE, or the run carried nothing out. The last is not defensive coding — an offer to double
zero is a button that lies about what it does. The online one is the platform's rule meeting
ours: an ad freezes this client, and a lockstep session cannot wait (`design/06`), so
`AdController` refuses one outright and a button that cannot work must not be drawn.

### The seam, and why the portal's own shape survived it

`PortalSession`'s header states the shape volume 41 chose: the game does not know the portal
exists, everything is derived from the phase stream once per frame, and removing the target costs
one entry point and one directory. A rewarded ad is the one thing that shape does not reach,
and it is worth naming why rather than treating it as an exception: everything else the portal
wants is something it needs to be **told**; an offer is something the player has to be **shown**,
on a screen the game owns, with a reward that lands in the meta layer.

The answer was the pattern this client already uses three times over (`setUiAudio`,
`setMusicAudio`, `setHostKind`): a capability **declared game-side** and installed by the entry
point. `client/src/platform/rewardedAd.ts` is a module-level registry with a two-method interface;
`crazygames/portalRewardedAd.ts` adapts `AdController` to it; `main.crazygames.ts` installs it
after `portal.start()`, because that is where the adblock probe runs and the probe is what decides
whether the button is drawn. `src/game/` still imports nothing from `platform/crazygames/`.

`portalRewardedAd.ts` exists as a *function* rather than an object literal in the entry point for
a reason worth generalising: an entry point runs `boot()` at import, so nothing written there can
be reached by a test. Three lines moved out of it are three lines under test — and one of its four
cases passes the REAL `AdController` through, so "the shapes match" is not a claim about a fake.

### The rule the platform's own frequency cap does not cover

`AdController` deliberately tracks no frequency: the SDK enforces "one midgame every three
minutes" and a second timer could only disagree with the authoritative one. A rewarded ad,
though, does not count against that cap — so watching one and then pressing CONFIRM handed the
player a second ad seconds later. Two individually legal calls, one outcome the requirements page
rules out by name ("comes as a surprise").

`REWARDED_MIDGAME_COOLDOWN_MS` (60 s) suppresses the automatic midgame after a rewarded ad the
player actually **watched**. Stamped from the outcome, not the request: an unfilled request cost
the player no time, so it must not cost them the ordinary break ad. That distinction is its own
test, and it is the case a plausible implementation gets wrong.

### The screen half

`Screens.ts` gains one optional `ResultOffer` — a label and a `claim()` — and three promises: the
button exists only when there is an offer, it is **one-shot**, and it leaves the screen before the
numbers change. `claim()` resolves with lines in *both* outcomes, on purpose: a player who pressed
a button and watched nothing change cannot tell the offer from a broken button, so an unfilled ad
says so ("No ad available - your 4 materials are safe") instead of silently reverting.

The offer takes a row of its own and pushes the two exits down by 56 px rather than squeezing in
beside them; with no offer every position is byte-identical to what this screen has always laid
out, which is why the existing layout-regression tests did not move. The taller variant was added
to `viewportFit.test.ts` with the **longest locale's** label (Russian, `autoWidth`), so the offer
row is now the Screens variant the menu fit has to clear — the same reason `storeEnabled: true` is
the Forge variant in that sweep.

### Verified live, not inferred

On the portal dev build with the real SDK reporting `local` (the first attempt reported
`disabled`, which is `SDK_WAIT_MS` expiring on a cold CDN fetch — a warm reload answers `local`):
a forced extraction carrying 4 materials drew the amber offer; a real tap ran a real
`sdk.requestAd('rewarded')`; the row became `Materials banked: 8 (ad bonus x2)`; the account bank
went `mat_fire@0: 4` → `8`; the button retired and CONFIRM/MAIN MENU closed the row it had
occupied; `app.ticker.started` was `true` afterwards and `ads.isShowing()` `false`, so nothing
leaked a suspension; and a midgame requested immediately after came back
`{played: false, reason: 'too-soon'}` — the cooldown firing on a live page, not only in a test.

**Tests: client 5264 (was 5218), repo 8710 green**, `npm run check` and `npm run check:logic`
clean, coverage 97.53% lines / 92.57% branches over 243 client files (two new files, both
covered). Three new i18n keys across all eight locales.

**Still open on this target** (`design/20`): a registered portal domain, without which real
banner fill and real ad playback cannot be settled; a hosted privacy/terms URL; the upload
itself. A second rewarded placement is deliberately unbuilt — it is a second balance decision,
not a second call site.

## The report that closed by not happening (2026-09-07, docs only, no code change)

*"拾取不到掉落物的报告 这个我这几天测试发现已经修复了"* — the unpickable-loot report, open since
v47 and carried through four rounds of engine sweeps, is closed. Several days of play on builds
carrying v51 and the symptom has not recurred.

**v51 was the report.** `DoorSystem.rebuildWalls` is the only thing in the engine that moves a
wall mid-run, and an item lying in a passage when its door locked was sealed inside stone with
nothing re-clamping it — a mob dying on a threshold, or a weapon swapped in a doorway, then the
room activating. Fixed by re-clamping every alive pickup at `dropClearance()` after the rebuild.

**How it closed is the part worth recording.** Not by a measurement and not by the recorded run
four rounds of sweeps had been asking for, but by the *absence* of the symptom over real play.
Three docs had to be corrected for that, and they are the three places a resolved report leaves
stale scheduling prose: `design/18`'s two "Still open" notes (one saying nothing in the engine
explained it, one saying v51 was a candidate and not a verdict) and `current-state.md`'s
"Whether v51 is *the* report is still unknown and still needs a recorded run". The engine's own
`ENGINE_VERSION_HISTORY.md` v51 entry needed nothing: it describes a mechanism and a fix, and a
history entry that does not schedule anything cannot go stale.

The sweeps were not wasted, and this is not an argument against them. They are what reduced the
candidates to one: four correct zeroes over 903 real drops and every death cell on five floors are
why v51's mechanism was *the* remaining explanation rather than one guess among several. What
changed is only which instrument closed it. **The replay ask stays the right ask for the next
report of this shape** — a seed does not reproduce a drop position, and F9 exists precisely so the
next one arrives with its input stream attached.

## The backup procedure stops being a sentence in a README (2026-09-07, server + deploy + docs, no engine change)

Two SQLite files hold the only two facts this project cannot regenerate: `accounts.db` (who
somebody is — identity, ladder, meta) and `billing.db` (what they paid for — orders,
entitlements, the outbox). Both sit on one disk on hardware this project *borrows*. The backup
procedure, in full, was two `scp` lines under "Ops" in `server/deploy/README.md`: a procedure
exactly as reliable as somebody remembering it, over the data a launch makes irreplaceable.

### Why it is a compose SERVICE and not a cron entry

This is the decision the rest follows from. The obvious implementation is a host cron job
calling a shell script — and on this box a host cron job is a **manual install nobody re-does**.
The CI deploy key runs one forced command that installs `dist/` + `Dockerfile` +
`docker-compose.yml`; anything outside that payload has to be put there by hand, once, by
somebody who then has to remember it again. That is the failure class `design/19` §9 already
records under a different name — *a value written into an env file is not a value the process
can see*.

So the worker is a **fourth entrypoint** (`server/src/backup/`, bundled to `backup.mjs` by the
same `scripts/build.mjs`) and a fourth compose service. It rides the deploy that already
exists, and its arrival is what proved that deploy can change service topology at all.

### Four properties, each with the test that fails when it is dropped

- **`VACUUM INTO`, not `cp`.** A copy of a database another process is writing captures a torn
  page set: it opens fine, reports a plausible size, and fails on the one page that mattered.
  `VACUUM INTO` runs inside a read transaction, so the destination is a point-in-time
  consistent snapshot taken with no cooperation from and no interruption of the running
  service. `backup.snapshot.test.ts` pins the point-in-time half directly: a row inserted
  between two cycles is in the second snapshot and not the first.
- **The worker cannot write to a live database.** Probed rather than assumed — `VACUUM INTO`
  works through a `readOnly: true` `node:sqlite` handle — so both data directories are mounted
  `:ro` and the only writable mount is its own volume. A test asserts the source bytes are
  unchanged AND that the source is still writable afterwards (an accidental read-write open
  shows up as a lock on Windows). The manifest test reads the `:ro` off the compose file,
  because a dropped `:ro` is invisible until the day the worker has a bug.
- **A snapshot is verified before it is published.** `PRAGMA integrity_check` on the *copy*,
  then gzip, then an atomic rename — so the directory never holds a file that merely looks like
  a backup. An interrupted run leaves a `.part`, which the pruner neither counts nor deletes.
- **Retention is per SOURCE and only advances on success.** A directory-wide `keep` lets a busy
  database age out the other one's history; pruning on schedule regardless of the cycle's
  outcome turns a retention policy into a countdown to having nothing. `prunable` is a pure
  function with a case table for exactly this reason — it is the one function here whose bug
  destroys data rather than failing to protect it — and one of its cases is that it ignores
  every file it did not write (a hand-made copy somebody is examining, a `.part`, a restored
  `.db`, the status file, a README: "delete the oldest files in the directory" deletes all five).

### The other half of the problem is being VISIBLE

A worker with no port is a worker nothing polls, and "the backups quietly stopped" is the
canonical way this fails. Each cycle publishes `status.json` (atomically), and the same bundle
answers `node backup.mjs --health`, which is the container's healthcheck. Three ways to be
unhealthy, and the third is the one worth having: no status at all, a cycle where any source
failed, or a status that is simply **too old** — without that rule a worker whose loop died
after one good cycle reports green forever off a stale success. `ci-deploy.sh` now asks for a
healthy cycle after `docker compose up`, beside the three `/health` polls, so a deploy that
silently stops backing up fails in CI — which is what that script's own comment already
demanded ("a silently failed deploy is exactly as bad as a silently failed backup").

It also **refuses to start** with no source configured, exit code 2, rather than idling green:
an empty `DDU_DB_PATH` counts as unset, since `?? fallback` only checks for nullish and a
compose file with a trailing `VAR:` produces exactly that.

### What the manifest gate needed, and why it was not just widened

`deploy.manifests.test.ts` hardcoded three services in five places — the sorted name list,
`PORT_VAR`, `expose` having exactly one entry, the healthcheck containing `/health`. A worker
satisfies none of those. It would have been easy to derive "HTTP service" from "has a
`PORT_VAR` entry"; instead the file now carries two explicit lists, `HTTP_SERVICES` and
`WORKER_SERVICES`, so **adding a service forces a decision about which kind it is** — derive it
and a new HTTP service that merely forgot its port silently becomes a worker with no port
assertions at all. Two new cases came with it: a worker must expose nothing and must
healthcheck its own bundle (with `--health`, naming the same file its `command:` runs, so the
health rule cannot drift into a second inline implementation), and every `./data/` mount on the
backup service must be `:ro`. That mount check needed two goes — two greedy `\S+` groups made
the mode field the whole container path, and matching every bullet in the block swept `- wnet`
in from `networks:` as a fourth mount, caught by an exact length assertion rather than a `>= 2`.

`deploy.bundle.test.ts` gained the end-to-end half: build the real bundle, run it as a bare
`node` process against a real seeded SQLite file with only the deploy manifest's dependencies
staged, wait for its `status.json`, **gunzip what it actually wrote and read the row back**,
then ask the same bundle for its health verdict in a second process — plus a case that the
bundle exits 2 with `no databases to back up` when misconfigured. Also asserted: the bundle
imports `node:sqlite` and does NOT import `ws`, since a websocket library bundled into a
process that opens no socket is the tell that an entrypoint is pointed at the wrong source file.

### One thing found in the deploy script that was not part of the task

`ci-deploy.sh`'s header claimed **"`docker-compose.yml` and `.env` are never touched"**, and
argued from it that the deploy key therefore cannot ship a compose file that bind-mounts the
host's `/` into a container to reach host root. The code copies `docker-compose.yml` — it has
for as long as the manifest test has asserted the payload list — so the claim was false, and
falsely reassuring, in the one comment about that box's security posture. Corrected to describe
what the code does, with the capability named, its bounding facts stated (the file is tracked
and reviewed like code; the same key already ships `dist/*.mjs` and the `Dockerfile`, i.e.
arbitrary code inside the containers either way) and the exact change written down for whoever
decides the borrowed box should not grant it. Deliberately NOT "fixed" by dropping compose from
the payload: that is the box owner's call, and this pass depended on the capability to deploy a
new service at all.

**Tests: server 1031 to 1091, repo 8770 green**, `npm run check` clean, coverage 98.90% lines /
97.88% branches over 52 server files (five new files, all covered). Two `checkDocPaths`
allowlist entries, each with its reason (`backup.mjs` is build output, `status.json` is runtime
output).

**Still open, and filed as such** in `server/deploy/README.md` §7: nothing is copied OFF the
box. A snapshot beside the database survives every failure this project has actually had and
none of the ones that take the host with it — and on borrowed hardware that is a real scenario.
The off-box copy needs a destination somebody owns, so it stays a human step rather than a
guess.
