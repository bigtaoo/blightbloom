## The docs were right about behaviour and wrong about every pointer (2026-09-03, docs only, no engine bump)

From a live question with no bug attached to it — *"look at the current technical docs and see whether they still match the code"*. Not
"fix X", just: are the docs still true? That is a hard question to answer honestly across
~1.5 MB of Markdown, so the pass was built as sweeps first and reading second.

**What was actually checked.** Three mechanical sweeps, each cheap enough to re-run:

1. **Every backticked path reference** in `design/` + `README.md` + `CLAUDE.md` — 921 unique
   path-shaped tokens — resolved against `git ls-files`, by basename and then by path suffix.
2. **Every relative Markdown link** across the same set, resolved on disk.
3. **Every `SCREAMING_CASE` constant** quoted in a decision doc, compared against its own
   `const NAME = <number>` definition in `engine/`/`client/src`/`server/src` (345 definitions
   collected, then matched against same-line numbers in the docs).

Then targeted structural checks on the contracts the docs claim to *own*: design/08's step
order against `GameEngine.step()`, design/07 step 7 against the shipped v53 melee window,
design/16 against `AuthService`/`db.ts`, design/17 against the locale files.

**The shape of the result is the interesting part.** Sweeps 2 and 3 came back **completely
clean** — zero broken links, and zero constants quoted at a stale value. Sweep 1's 35 hits
were almost all correct: a reference to `FloorProgress.ts` or `arena_prototype_60.json` framed
explicitly as retired-and-deleted, a reference to `engine/loop.ts` or `net/InputSource.ts`
correctly attributed to the sibling project `funny`, and — best of the lot —
`client/.../standingCoverParity.test.ts` in design/18, which is a **deliberately recorded**
phantom citation: that doc already documents that commit `14e693b` cited a test that was never
created. The audit's own tooling flagged a finding the docs had beaten it to.

So the prose about *behaviour* held up. Everything that was wrong was a **pointer**: a file
path, a step number, a mode tag, or a count. Never a description of what the code does. That
is worth naming as a class, because it says where to look next time.

**The one that mattered.** design/08 calls its `step()` skeleton "the determinism contract",
and it was wrong twice over:

- **`DoorSystem` (11.5) was missing outright** — not mis-described, absent. It appeared nowhere
  in design/08, while `GameEngine.ts` has run it between spawns (11) and extraction (12) since
  `ENGINE_VERSION` 35, and `DoorSystem.ts`'s own header explains why both sides of that
  placement are hard requirements (a room's enemies for *this* tick must be counted before
  locks are decided; `ExtractionSystem`'s capstone check must see this tick's fresh
  `hasLiveEnemy`). Added to the skeleton with an ordering note, including the detail that its
  wall rebuild is the only thing in the engine that moves a wall mid-run — which is why v51
  had to re-clamp resting pickups after it.
- **`- **PvP** skips steps 2, 10, 11, and 12` was wrong on three of the four.** Only 12 was
  right. An arena room carries enemies, so **2** drives them (only the dungeon
  room-activation gate inside `AIDecideSystem` is PvE-specific); **11** is the shared
  `WaveScript` path for *both* dungeon and arena rooms, and is what drops an arena room's
  `lootMarker` crates on activation; and **10** is the most arena-aware of the three — it
  rolls an unresolved crate through `rollArenaDrop`, scales a picked-up weapon by
  `PVP_SCALE_FACTOR`, and owns the PvP-only `bandage`. Rewritten as what each mode *actually*
  skips: PvP skips 11.5 and 12, PvE skips 8a/8b, everything else runs in both.

**A systematic one, in the code's own comments.** Chasing the above turned up that three
systems never got renumbered when `StatusEffectSystem` was inserted as step 8 at
`ENGINE_VERSION` 8. Each was off by one against both `GameEngine.step()` and
`StatusEffectSystem`'s own header, which correctly refers forward to "death & drops (step 9)":

| file | header said | actually |
|---|---|---|
| `DeathDropsSystem.ts` | Step 8 | **9** |
| `PickupSystem.ts` | Step 9 (and "a kill in step 8") | **10** (a kill in step **9**) |
| `SpawnSystem.ts` | Step 10 | **11** |

Two of those headers also claimed `(PvE only)` — `AIDecideSystem` and `SpawnSystem` — which the
design/08 correction above had just disproved. All five fixed.

**The other four, smaller.**

- **design/10** documented a compile-time gate that no longer exists. It stated as a live rule
  that screens are driven only by their buttons per `screens/confirmEdge.ts`, and that
  `confirmEdge.test.ts`'s exhaustive `Record<Phase, boolean>` "fails type-check until a
  newly-added phase is explicitly given `false`". Both files were deleted 2026-08-17
  (`8b8cfc6`), `GameLoop.ts`'s `pollConfirm`/`prevFire` poll went with them, and `Phase` moved
  to `game/phase.ts`. Rewritten to the current invariant — *no* screen accepts a fire-edge
  confirm now, the result screens having been the last holdout — keeping the 2026-08-02
  mouse-down-race rationale, which is still why the rule exists, and adding an explicit note
  that the gate is gone: the invariant now holds **structurally** (there is no fire-confirm
  path to opt out of) rather than by a table, so nothing fails to compile when a phase is
  added. That warning is the actual deliverable; the stale path was the cheap half.
- **design/03 contradicted design/07 and the code**, on the pass that had shipped the day
  before. It said `swingTicks` reaches the render layer because "`melee_swing` carries it". It
  does not — the event is `{ownerId, faction, gx, gy, facing}`, and both design/07 step 7 and
  `engine/state/events.ts`'s comment say the omission is deliberate: every client holds the
  whole state, so an event field would be a second source of truth for a number the reader
  already has. Corrected, with the reasoning rather than just the fact.
- **design/17** called `locales/zh.ts` "the first (and today, only) translation" while the same
  doc says "all 8 locale files" and "all eight shipped locales" four times further down. There
  are seven translations plus canonical `en.ts`. Fixed, and tied to the later wording.
- **Two version facts.** `roadmap/current-state.md` said "Five engine bumps have landed since"
  (47–51) with the engine at 53 — v52/v53 summarized in. And `engine/versionHistory.ts`'s own
  doc comment advertised the history file as covering "why v2 through v43 each bump" at "~500
  lines"; it covers through v53 at 1344. Reworded to "every bump from v2 onward" so that half
  cannot go stale again.

**Verification.** Engine `tsc --noEmit` clean and 1137 tests green — the engine changes are
comment-only, so this is a check that nothing was corrupted, not evidence of behaviour. The
file-length gate passes in every workspace.

**What this pass did NOT do, honestly.** No test was added, so **none of this is gated** and
the same drift can recur the same way. Two of the four classes found here are mechanically
checkable and worth a real gate later: a doc's backticked path references resolving against
`git ls-files`, and each system's self-declared `Step N` header agreeing with its call position
in `GameEngine.step()`. The second would have caught the off-by-one trio the day it appeared,
and is a handful of lines — it is the one worth doing. The mode tags (`[PvE only]` and friends)
are not mechanically checkable against a `state.*Enabled` gate without more cleverness than the
problem deserves.

## Every door is the same door, whatever wall it is cut into (2026-09-03, client only, no engine bump)

Live report with a screenshot of the shipped `forge → extraction` doorway on floor 1: *"some doors get
covered by the wall — I would like a door's presentation to be its own, and the same, however thick the wall is"* — some doors get covered by the wall;
a door's presentation should be its own and uniform no matter how thick the wall is.

**"Covered by the wall" reads as an occluder bug, and it was not one.** The two clips that exist
for exactly that (`bordersDoorNorth` / `effectiveWallHeight`, ROADMAP 2026-08-20) were both working
and both still fire. Sweeping the 24 shipped doors through the real pipeline instead produced two
presentations with almost nothing in common: 13 east-west passages (`64x128`, travel east-west)
drawn as a 64 x **104** portrait opening, and 11 north-south ones (`128x64`, through the low
boundary between two vertically stacked rooms) drawn as a 128 x **22** letterbox under 64 px of
their own cap stone. `doorFlankTier` gave a door the height of the SHORTEST run abutting its
passage, and that boundary is a `WALL_H_KERB` on both sides. **The wall covering those doors was
their own lintel** — a fixture three-quarters stone, showing 12% of its own leaf art.

**A door stops being a course of wall and becomes a fixture with a fixture's constant.**
`wallGeometry.DOOR_H`, one height for every door in the game, `WALL_H_PERIMETER` rather than a
fourth independent number — which also keeps `MAX_WALL_HEIGHT` (what `GameLoop.cameraFrame` pads
the framed room rect by) correct by construction. `doorFlankTier` and its `abutsAlongGap` helper
are deleted rather than left unused, and `DOOR_TIER` (declared beside `DOOR_H`, not in
`RoomBuilder`) is the tier a door is handed to `wallJoins` as, because that pass reasons in tiers.

**What it spends, and why it is affordable.** `WALL_H_KERB` is 22 precisely because a room's floor
lies immediately north of that boundary and anything tall there stands between the camera and the
player. A door standing 104 there covers ~82 px more of that floor. It is paid for by the door's
own x-ray, which it has had since it started standing (`buildDoors` registers every fixture as a
`fadeableBlock`, cap layers and deep layers both) — and it is the same deal the other 13 doors have
always run at. **The kerb itself is untouched**: `DOOR_H` is a door constant and no wall run reads
it, which `RoomBuilder.test.ts` asserts as the control beside the height. The drawn WIDTH is
deliberately unchanged: an opening still takes the passage's own screen footprint, because a fixed
aperture on a 128-wide gap would paint stone over floor the player can walk on.

**Verified as a real frame, not by looking at code**: `renderer.extract` on the live floor with the
player parked north of that doorway, before and after at identical framing — before, a dark red
hairline along a stone lip; after, a full hazard door. Plus the closest legal approach (the cap
x-rays and the body reads through it) and an east-west door unchanged.

**Tests: 38 distinct mutants, 38 killed** across two rounds, baseline green, revert in `finally`.
Round one authored 34 over the whole door path — 26 killed, 5 survived, 3 skipped on anchors that
matched twice. Four of the five survivors were one shape, the one `drawDoorWear`'s `WEAR_ALPHA`
taught this repo in 2026-08-26: **the layer's geometry covered and its VALUE by nothing at all.**
`OPEN_RECESS_ALPHA_TOP` set to the LOCKED 0.72 (an open tunnel stops reading as floor — the defect
the 2026-08-30 pass exists to fix) and `SILL_ALPHA` / `GLOW_WASH_ALPHA` / `RIM_ALPHA` each to 0,
all with every "present, ramps, right state" assertion green. The fifth was `RoomBuilder` handing
the doors the WALLS' joins (`.slice(0, n)`), invisible because no fixture had a door whose joins
actually CLIP its cap. All five closed, and each new assertion was itself mutated to prove it has
teeth. The last "survivor" was a harness bug — `push(...).valueOf()` still pushes — and dies to 4
tests once the mutant is a real no-op. **+5 tests (client 4534 → 4539.)**

Two of the new tests are assertion CLASSES this suite did not have. **How much of the leaf survives
the crop**, swept over all 24 doors against the real IHDR of the shipped PNGs: every door must show
over half its own art, and at the old height it reports 12% and fails — the first test in the door
suite that would have *caught* the report rather than described it afterwards. And **the x-ray
actually fires at a kerb doorway** (`simRenderParity.test.ts`, beside the kerb's own exemption):
same focus construction, same rule, opposite verdict, over all 11 at every drawn body height, plus
the deep pass for a character standing IN the passage and the flanking kerbs still not firing as
the control. That is the claim `DOOR_H` is written on, and it was prose until now.

**A stale constant the leaf test found on its way past**: `doorRender.ts`'s header had said the
door swatches are "221x320-ish" ever since the same 2026-08-20 pass re-trimmed their transparent
margins down to 147x217 and 156x224 — which made the crop look twice as generous as it was, and
which this entry's own first draft repeated. The test reads the shipped IHDR, so it cannot go stale
again. Same class as this volume's audit above: the behaviour was right and the pointer was wrong.

## The step numbers get a gate, and it fails on its own first run (2026-09-03, engine tests + docs, no engine bump)

Direct follow-up to this volume's first entry, which named exactly one of its four findings as
worth a real gate and then did not write it. This is that gate: `engine/stepOrder.test.ts`,
Layer 0 beside `determinismLint.test.ts` (design/18).

**What it enforces, and what it deliberately does not.** The step ORDER is already enforced —
reorder a system and the golden hashes move. What nothing enforced is the three places that
*describe* that order: each system's `Step N — …` file header, the `// N` label on every call in
`GameEngine.step()`, and design/08's skeleton. Four rules:

1. every `step()` call carries a label and resolves to a field something constructs;
2. the labels **strictly increase** down the body — a call moved without its number failing here
   is the only one of the four that could precede a real behaviour change;
3. every system header's declared number equals its call position;
4. no `engine/systems/*System.ts` is missing from `step()`, and none is called without a file.

Plus the doc half: design/08's skeleton must list exactly the labels `step()` runs — the rule that
would have caught `DoorSystem` (11.5) being absent from that list for four weeks.

**The label comparator is the one piece with real content.** A step label is not a number: the
shipped order runs 1..8, `8a`, `8b`, 9..11, `11.5`, 12..14. Both escape hatches are deliberate —
inserting a pass would otherwise have churned every header and every design/08 citation below it —
so the comparator sorts on `[numeric, suffix]`, which puts `8 < 8a < 8b < 9` and `11 < 11.5 < 12`.
A plain string compare would rank `'10' < '9'`, and there is a test that asserts precisely that
wrongness to document why the comparator exists.

**Two real defects fixed to make the gate pass** — both found by writing it, neither by the audit:

- `ZoneSystem` and `EnvironmentSystem` opened with a bare `Step —`, no number at all. Now `8a`
  and `8b`. This is a third shape of the same drift, and the sneakiest: the trio in the entry
  above at least claimed *a* number.
- **design/08 called 8b "[PvP, arena-mode only]", and it is not** — nor is it since 2026-08-04.
  `EnvironmentSystem.tick` returns early only when *neither* `zoneEnabled` *nor* `dungeonEnabled`
  is set, because it grew a per-actor `roomId`-tracking half for the dungeon, and that half is
  what `DoorSystem` (11.5) reads to decide which rooms hold live enemies. In a PvE dungeon 8b is
  load-bearing, not a no-op. **The first entry in this volume got this wrong too** and shipped
  "PvE skips 8a/8b" in its own correction — a mode tag copied forward one more time while
  rewriting the sentence around it. Fixed in both places. It is also precisely the class the new
  gate cannot see, which is why that entry's note about mode tags stays as written.

**The gate found the known comment trap on its very first run**, which is the part worth keeping.
`GameEngine.ts`'s header says *"step(commands) is the direct entry (headless/tests)"*, so
`indexOf('step(commands')` matched the **prose**, ran to the constructor's closing brace, and
returned the seventeen field declarations as the step order: seventeen systems, zero labels, four
green rules, and a contract test that checked nothing. It now matches on the `commands:` type
annotation, which the prose has no reason to carry. `determinismLint.test.ts`'s own header records
this same trap from a different pass — a source-text gate matching a value quoted in a comment —
and it still cost a debugging round, so the case is pinned by a test of its own.

**Tests: 23, and the parser lives in `fixtures/stepOrder.mjs` so they can be real.** A contract
test whose only evidence is "zero problems against the real tree" is indistinguishable from one
that checks nothing, so every rule is also fed a synthetic source that violates it, against a
minimal two-system control that passes. Then the same rules were run against the **real** tree
with each fix reverted one at a time, baseline verified green first and restored in `finally`:

```
DeathDropsSystem claims 8   KILLED    ZoneSystem bare "Step -"        KILLED
PickupSystem claims 9       KILLED    EnvironmentSystem bare "Step -" KILLED
SpawnSystem claims 10       KILLED    an unorderable label (10x)      KILLED
design/08 omits 11.5        KILLED    design/08 lists a 11.6          KILLED
```

8 of 8, including both of the original findings. The vitest-through-Python harness hit the Windows
cp1252 trap on the way (`UnicodeDecodeError` reading child stdout, which reads as ALL-CRASHED
rather than as a harness bug); judging on the **exit code** instead of parsing stdout is the fix,
and the `finally` had already restored every file correctly. 1160 engine tests, `tsc --noEmit`
clean, `check:filelength` green.

**What is still not gated.** The mode tags (`[PvE only]`, `[both modes]`) — the very thing this
pass got wrong again above. Checking one means reading a system's early-return and deciding which
`state.*Enabled` flags it tolerates, and `EnvironmentSystem`'s `!a && !b` is already the case a
naive version would misread. Also ungated: a system header's prose cross-references to *other*
steps (`PickupSystem`'s "a kill in step 9"), which is the same class as the numbers but with no
anchor to compare against. Both stay review-only, on purpose.

## The path references get a gate, by giving up on two thirds of them (2026-09-03, tooling + docs, no engine bump)

The second and last of the two gates this volume's audit named. `build/checkDocPaths.mjs` +
`build/checkDocPaths.test.mjs`, wired as `npm run check:docpaths` and folded into `npm run check`
between the WeChat package gate and the test run. (Placed in this volume rather than the
higher-numbered `17` because `17`'s own header assigns the *pointers* half of the day to `16` —
theme beats number, `ROADMAP.md` rule 2.)

**Why this one was harder than the step numbers, and what the answer was.** The raw sweep found
36 unresolved path tokens across the whole doc set and **35 were correct**. A gate with that
false-positive rate is worse than none: the allowlist would be the artifact, and the honest
reading of a red run would be "add it to the list". So the useful question was not how to make
the sweep smarter but **which docs the rule should apply to at all.**

The answer is that `design/ROADMAP.md`, `design/roadmap/*` and `README.md` are an **append-only
historical log**, and an August entry naming `FloorProgress.ts` is not stale — the file really
was there, and this repo's convention is to *supersede* a log entry rather than rewrite it.
Gating history against today's file list would mean either editing the past or carrying an
allowlist that grows with every deletion, forever. Meanwhile the one real defect the audit
found — `design/10` promising a `confirmEdge.test.ts` type-check gate deleted a month earlier —
was in a **decision doc**, the kind that describes the current system and gets read as
instructions.

So the gate covers `design/**/*.md` minus ROADMAP and the log volumes, plus `CLAUDE.md`: 26 docs,
973 references, **20 allowlisted**. Dropping two thirds of the corpus is what turned an unusable
sweep into a gate, and it cost nothing that was ever going to catch anything.

**The rule is basename-only, deliberately.** `game/Scene.ts` for
`client/src/game/scene/Scene.ts` is house style, not drift, and full-path matching would flag
~200 correct references. Resolution is against `git ls-files` — tracked files only, so the answer
is identical on every machine and in CI, where a filesystem walk is not (`client/dist/version.json`
exists after a build and not before). The consequence is worth knowing: **`git add` a new file
before citing it in a decision doc**, or the gate fails.

**The 20 exemptions, and why none of them is a shrug.** Four are the sibling project `funny`
cited by *its* paths (`engine/loop.ts`, `net/InputSource.ts`, its `claudedocs/`) — real files,
wrong repo. Four are Pixi internals design/04 names as the *cause* of a WeChat behaviour
(`GlTextureSystem.mjs` gating mipmaps, and friends). Three are generated or gitignored (`synth.json`,
`project.private.config.json`, and `client/dist/version.json` — which the gate caught me citing
in design/18 mid-pass, on its own rule). Three are not paths at all and never were —
`.sim.ts` is a filename *suffix*, `zh.json` a generic example in CLAUDE.md's language policy
(this repo's locales are `.ts`), `/audio/death-player_NN.mp3` a URL pattern with a placeholder.
Five are deleted files a decision doc cites **as deleted**, which is the whole point of those
sentences. And one is a phantom the docs deliberately record as a phantom: design/18's note that
commit `14e693b` cited a `standingCoverParity.test.ts` that was never created.

Each entry carries a `why`, and the list is **asserted minimal** — an entry whose token stops
being cited, or starts resolving, fails the gate. That assertion is the difference between an
allowlist and a slower way of having no rule, and it is the same one `determinismLint.test.ts`
makes about its own.

**What it cannot do, stated plainly because the allowlist is the reason.** The exemption is on a
TOKEN, not a sentence. Five entries are deleted files cited as deleted — and if someone rewords
one of those into a present-tense claim, which is *exactly* the defect that motivated this gate,
the token is still allowlisted and the run stays green. It cannot read framing. What it does
catch is a **new** dangling reference appearing in a decision doc, which is the direction the
drift actually travels: something gets deleted or renamed, and a doc elsewhere keeps naming it.
The framing half stays a review concern, and the `why` strings are where that judgement lives.

**Tests: 19, plus 4 mutants against the real tree.** The synthetic half drives the checker with
injected docs and file lists, so every rule is proven to fire — a dangling reference reported with
its doc and line, a shorthand path accepted, an allowlisted token ignored, a dead entry and a
now-resolving entry each reported, and the scope proven to exclude the log and include
`design/rendering/`. The token extractor is pinned against the two things it must not match:
backticked prose that is not a path (`GameState`, `step()`) and dotted numbers (`11.5`, `0.2`),
of which these docs are full. Then, against the real repo:

```
dangling ref added to a real decision doc          KILLED
design/10 cites confirmEdge.test.ts, no exemption  KILLED   <- the original defect
an allowlist entry nothing cites                   KILLED
an exemption whose token resolves                  KILLED
```

`npm run check:docpaths` green, root build tests 63 passed, and the gate re-verified green after
volume `17`'s coherence audit merged onto main — the two passes touched the same decision docs
without colliding.
