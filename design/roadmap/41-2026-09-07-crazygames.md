## The CrazyGames build target (2026-09-07, client + build + docs, no engine change)

Asked as a question — *"距离发布 crazy games，还缺少什么？整个游戏流程贯通了吗"* — and then as
an instruction to close every gap in order. The audit half is worth recording first, because
the answer to the second question turned out to be the easy one.

**The flow was already whole, and it was verified rather than believed:** boot → main menu →
SELECT MODE → SOLO PvE → Forge → START RUN → a live room with real enemies and a HUD reading
`FLOOR 1/5` `ROOM 1/5` `FOES 8`, zero console errors, and — importantly for a portal — zero
network requests, so a solo run needs no backend at all. `npm run test:pve-sim`'s seven gates
were green including *"nothing softlocks — a run always ends in a real outcome"*. The content
behind that flow is one biome (`ember`, five authored floors of 5/6/7/6/5 rooms, boss on the
last) plus one 60-room PvP arena plus the tutorial. Thin, not broken — and `ROADMAP`'s
Backlog B1/B2 (chests, and a real run-buff offering) remain the largest holes in the loop as
*designed*, which is a separate question from shipping.

**What was actually missing was a platform layer, and the word `crazygames` appeared zero
times in the tree.** Eleven gaps, closed in the order they were filed:

- **The SDK, absent entirely.** `client/src/platform/crazygames/` now holds it, split so that
  transport, policy, placement and the DOM element are four files with four tests:
  `sdk.ts` (a façade in which every call is a no-op when the script is missing, every wait is
  bounded, and no failure path can reach a caller — an ad network may not be able to end a
  run), `AdController.ts` (the rules: never during gameplay, never during an online match,
  muted and frozen for the duration, released in a `finally`), `BannerHost.ts` (one 320×50
  container, main menu only, hidden AND cleared elsewhere, 30-second refresh floor),
  `GameplayBracket.ts` and `PortalSession.ts`.
- **Absolute asset paths.** Two halves, and neither covers the other: `base: './'` in
  `vite.crazygames.config.js` fixes the paths Vite writes, and `baseAssetHost` in
  `render/assetHost.ts` fixes the ~200 absolute `'/skins/…'` paths this repository's own
  source contains. The rewrite deliberately produces `skins/x.png` and not `./skins/x.png`,
  because `platform/web/webMusicDeck.ts` tests `el.src.endsWith(url)` to decide whether a
  deck already holds a track — `el.src` reads back absolute, so a `./` prefix would never
  match and every loop wrap would restart a multi-megabyte download.
- **An external checkout the platform does not allow.** In-game purchases there are limited
  to invited games through the platform's own Xsolla account, and the Forge had a STORE
  button, a `[B]` key and 17 purchasable SKUs. `storePlatform.detectStorePlatform` returns
  `null` for a portal host, so the entry is not rendered and the key is not bound — the same
  fail-closed shape as its iOS 3.1.1 branch.
- **Four clicks to gameplay, against a one-click rule.** `MainMenu.setQuickPlay(true)` makes
  PLAY start a run with the meta's own loadout (the starter kit for a new player) and moves
  SELECT MODE to its own button, so co-op, PvP and the tutorial stay exactly where they were.
  `RunLifecycle.beginQuickRun()` is the entry point, and it art-gates for itself — a run with
  no screen between it and the gate would otherwise draw its first room out of placeholder
  rectangles.
- **Invisible touch controls.** `TouchControlsView` gated the whole control layer on
  `TouchVisual.active`, which was `everTouched` — set by the FIRST pointerDown. So a phone
  player opened the game and saw no joystick, no fire button and no weapon buttons until they
  had already guessed where to press. `TouchControls.setAssumeTouch` is the other half of that
  answer, declared by the platform (`WebInput` from a `(pointer: coarse)` probe — primary
  pointer, so a touchscreen laptop still gets no overlay; `WeChatInput` unconditionally).
- **`index.html`**: `lang="zh-CN"` → `en`, a title that still read *"Blightbloom — Vertical
  Slice"*, and the `user-select`/`touch-action` suppression the technical requirements ask for
  by name.
- **Arrow/space page scroll**, cancelled on every repeat of a held key (before the
  already-held early return, or a held arrow scrolls from the second event on) and yielding to
  a focused text field, because Space and the arrows are editing keys inside the login and
  party-code overlays.
- **No consent surface.** A one-line data notice on `LoginScreen`, in all eight locales —
  factual and derived from the code (a username, a password hash, the account's progress)
  rather than boilerplate, and placed at the only point in this game where anything about a
  player leaves the device at all.
- **No mute/pause bridge.** `audio/externalMute.ts` is a module sink — the third instance of
  the shape `audio/uiSound.ts` and `game/musicDirector.ts` already use, and for the same
  reason: the muter is installed from an entry point and the muted has exactly one authority
  (`game/settingsBinding.ts`), with a 500-line-capped `Game.ts` between them. It is a FACTOR
  over the settings and never a write to them, so an ad ending restores a player who had music
  at 25% to 25%, and a player who had muted themselves stays muted.
- **Auto-reload**, deliberately absent: the portal serves an immutable versioned upload from
  its own CDN, so there is no `version.json` to poll and reloading someone else's frame is not
  ours to do.
- **Size**, already fine and now recorded as a property to protect: 6.2 MB whole, and the
  initial download is only the `lobby` pack plus UI because of design/12's asset phases. The
  platform measures from page open to the first `gameplayStart`, so collapsing those phases
  back into one eager preload would move the number it grades.

### The design decision worth defending: the game does not know the portal exists

`PortalSession` derives everything the portal is told from ONE input — the phase, once per
frame, on its own ticker callback installed by the entry point, the way `src/perf/` installs
its brackets. Nothing under `client/src/game/` imports it. `Game.ts` (at exactly its 500-line
limit) and `GameLoop.ts` (20 lines of headroom) gained nothing.

The alternative was five hooks — `beginRun`, `quitRun`, the pause path, each gameover arm, both
sides of an ad — whose correctness is "nobody forgot one". `game/musicDirector.ts` already
records why this codebase rejects that shape for exactly this kind of derivation: it has two
failure modes, *a moment nobody remembered to hook, and a moment that fires twice*.

Two phases turned out not to be what they look like, and both were caught by the tests rather
than by inspection:

- **`settings` is a full phase that behaves like an overlay.** Opened from a pause it returns
  to that pause, so comparing against the raw previous phase read `paused → settings` as
  "left a run" and put a midgame ad over a run the player was coming straight back to.
- **`start()` resolves after the first frame.** The only `menu` transition of a session happens
  on frame one, while `init()` is still in flight, so the SDK gate was closed when it went past
  and the banner never appeared at all — found by running the built bundle, not by reading it.

### Three findings the SDK documentation does not contain

All from serving the real bundle from a sub-path and driving it. All the same class: **the
shipped SDK is not the documented SDK**, which is precisely the risk `sdk.ts`'s own header
names, so it is the risk the file was built to survive.

1. `SDK.environment` **does not exist** in the shipped v2.9.0 script — `'environment' in SDK`
   is `false`. The prototype carries `getEnvironment()` instead. Reading the documented
   property reported `disabled` on a page whose own console was logging `environment: local`,
   and the whole integration then did nothing whatsoever: no brackets, no banner, no ads, no
   error.
2. `getEnvironment()` **returns a Promise**. A synchronous read gets an object, fails the
   string check, and reports `disabled`.
3. `SDK.init()` **can never settle**. Unbounded, that means `PortalSession.start()` never
   resolves, `loadingStop()` is never called, and the portal shows a loading spinner over a
   game that has been playable for minutes. Every wait in `sdk.ts` is now inside one 3-second
   budget.

`__portal.diagnostics()` exists because of these — one console line reporting the environment,
the adblock probe and whether the brackets are flipping. It is the only instrument this
repository has for the half of the integration it cannot test.

### Verification, including the part that was asked for by name

Served from `http://127.0.0.1:8099/games/blightbloom/` — a sub-path deliberately, since that is
the shape absolute paths break under.

- Boots, loads all art, renders, no console errors.
- The real SDK loads and answers `environment: local`, its own console logging
  `Requesting game loading stop` / `Requesting adblock status` / `Requesting gameplay stop`.
- PLAY → a live run in one click, with `__portal.diagnostics()` reporting `· gameplay`.
- **Online play, verified against the deployed backend** (*"我希望能直接测试联机功能"*): PVP
  SOLO QUEUE → the server's 30-second practice-bot backfill → a real match, `ALIVE 2/2`,
  `zoneEnabled`, two seats, and the lockstep advancing **897 ticks in four seconds** of wall
  clock. Two live browser tabs could NOT be used for this and that is worth recording: a
  background tab's `setTimeout` is throttled to roughly once a minute, so the second client's
  matchmaking poll let its queue entry expire (`{"status":"expired"}` on both) while a manual
  probe stayed `queued`. The bot-fill path is the one that works from a single visible tab.
- One real bug found by that test and fixed: the portal build had no `VITE_MATCHSVC_URL`, so it
  inherited `runState.ts`'s `http://localhost:8788` — right for `npm run dev`, and the one
  default that can never be right for an uploaded bundle, where co-op, PvP, the ladder and
  accounts would all have failed to connect silently on a build that worked perfectly on the
  machine that made it. The portal config now defaults it to `https://bb.gamestao.com` and
  still honours an override.

### Tests

Seven new suites under `client/src/platform/crazygames/` plus additions to eight existing
files. Client suite 5203 → **5218**; whole repo **8664** green; coverage 97.52% lines / 92.56%
branches over all **241** client source files (241/241 measured, up from 224).

`portalBuild.test.ts` is the one worth naming, and it is `design/18` Layer 6's technique
applied to the client: it asserts against the real `index.html` and imports the real
`vite.crazygames.config.js` to exercise the config's OWN transform, rather than a copy of its
string surgery. It caught two things a module test could not:

- The HTML rewrite was on the wrong hook. `vite:build-html` has already replaced the entry's
  `src` with the emitted chunk by the time `transformIndexHtml` runs at `generateBundle`, so a
  `transformIndexHtml`-only plugin cannot swap the entry in a production build at all. The
  build failed on the plugin's own guard — which is the only reason it was not a silently
  mis-built bundle. The rewrite runs from `transform` (build) and `transformIndexHtml` (dev),
  is idempotent, and `closeBundle` fails the build if neither route fired.
- The guard needed a FRESH plugin instance to test: `applied` is per-build state, so sharing
  the one the config already built let an earlier test's successful rewrite satisfy a later
  test's "no rewrite happened" case.
