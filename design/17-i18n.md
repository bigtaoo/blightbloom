# 17 — Internationalization (i18n)

The project's first localization system. Shipped 2026-08-02 in response to a direct
request: the client had zero externalized strings (every UI string was a hardcoded
English literal in `client/src/game/*.ts`), and the request was specifically for
English to be the canonical index/key language, with other locales as translations
keyed off it — plus a repo-wide rule (recorded in `CLAUDE.md`) that all code, comments,
and docs stay English, with translation data being the one deliberate exception.

## Architecture: `client/src/i18n/`

- `locales/en.ts` — the canonical/source-of-truth locale. A deeply nested `const en = {
  ... } as const` object, namespaced by screen (`mainMenu`, `pauseMenu`, `settings`,
  `forge`, `hud`, `auth`, `party`, `results`, `toast`, `compareCard`, `card`). Leaf values are
  either plain strings or `{varName}`-style interpolation templates.
- `locales/zh.ts` — the first translation, and the one this doc's examples use. There are
  **seven** now (`de`/`es`/`fr`/`it`/`pl`/`ru`/`zh`), eight locale files counting `en.ts`
  itself; the rest of this doc says "all 8 locale files" and means these. Each is typed as
  `Translations<typeof en>` — a recursive mapped type requiring the exact same nested
  keys as `en.ts` with `string` leaves. A missing or extra key is a **compile error**,
  not a silent runtime fallback or an untranslated string that ships unnoticed — which is
  what makes adding the seventh translation no riskier than the first.
- `index.ts` — `t(key, vars?)`, `getLocale()`/`setLocale()`, `LOCALES`,
  `DEFAULT_LOCALE`. `TranslationKey` is a compile-time union of every dotted leaf path
  in `en.ts` (a `DotPaths<T>` mapped/template-literal type), so `t('forge.titel')` (a
  typo) fails `tsc`, not a manual QA pass.

## Semantic keys, not raw English strings

Keys are namespaced and semantic (`t('forge.title')`), not the English sentence itself
(`t('FORGE OUTPOST')`) — the option explicitly chosen when this was scoped. Editing the
English copy later never breaks another locale's key; a key is a stable identifier, the
English string is just `en.ts`'s own value for it like any other locale's.

## Where the live locale lives

`SettingsState.locale` (`client/src/settings/SettingsState.ts`) is the **persisted**
value — same `SettingsStore`/localStorage convention as `master`/`sfx`/`music`/`muted`.
The i18n module's own `currentLocale` is a live, in-process **mirror** every `t()` call
reads synchronously, so call sites never need a `SettingsState` threaded through them.
`Game.ts` calls `setLocale(this.settings.locale)` once at boot (right after
`settingsStore.load()`), and again immediately whenever the player changes it.

## Switching locale live: retext-on-show, not a global re-render hook

Most screens only build their static button/title text once, in the constructor —
positions get recomputed on every `show()`, but text didn't. Rather than add a
global "retranslate everything visible" mechanism, each screen got a small `retext()`
(or inline equivalent) that re-applies `t()` to its static labels, called from `show()`
(`MainMenu`, `PauseMenu`, `LoginScreen`, `PartyScreen`, `Screens`) or from `render()`
for screens that already re-render on every call anyway (`Forge`, `HudView`). A language
change is visible the next time a screen opens — not necessarily on the screen
currently open behind the Settings panel, which is an accepted, minor trade-off, not a
gap: the Settings screen itself (where the toggle lives) *does* update immediately.

## The `Settings` language control

`Settings.ts`'s `languageBtn` (same tappable pattern `muteBtn` already used) and always
displays the *current* locale's own name for itself (`English`/`中文`/`Deutsch`/…, from
a small `LOCALE_NAMES` map — language names are conventionally shown in their own
language, not translated). Tapping calls `setLocale()` immediately (so the button's own
next `syncWidgets()` already reads correctly) then feeds the change through the
existing `onChange`/`SettingsStore.save()` path, so it persists exactly like
volume/mute do. **Originally a 2-way `en ⇄ zh` toggle; since 2026-08-03's 8-locale
expansion, it's a `nextLocale()` cycle through `LOCALES`' declared order instead** (see
that entry below) — still a single button, no new widget, just steps through more
entries per tap.

## A real correctness bug this migration had to fix

`RunOutcome.ts`/`Screens.ts` used to decide the win/loss result icon by comparing the
result screen's own **title text** against English literals (`title === 'EXTRACTED' ||
title === 'VICTORY ROYALE'`). Once `title` became a translated string, that comparison
would silently always resolve to the loss icon in every non-English locale. Fixed by
threading an explicit `won: boolean` through `RunOutcomeHost.showOutcomeScreen` →
`Screens.show()`, decided once at the actual win/loss branch in `RunOutcome.ts` instead
of re-derived from display text.

## What's translated vs. deliberately not

Translated: every authored UI sentence/label — menu/HUD/forge/auth/party/results copy,
toast messages, compare-card stat labels, error/status text — **and, since 2026-08-15
(below), every content DISPLAY NAME**: weapon/character/material/buff names.

**Deliberately left as raw English tokens**:
- Internal catalog **ids themselves** (`repeater`, `vanguard`, `mat_fire`, `dmg_up`, …)
  and other enum/data-driven values with no authored display name of their own — weapon
  `kind` (`ranged`/`melee`, translated via `hud.kind.*`) and rarity tier are translated
  chrome, but a raw id used as a render/texture-lookup KEY (e.g. `weaponSkins.ts`'s
  `getWeaponTexture(spec.name, …)`) is never player-facing text and stays untranslated
  by construction.
- `net/auth.ts`/`net/party.ts`/`net/matchmaking.ts`'s internal fallback error strings
  (`` `auth request failed (${status})` ``, etc.) — these only surface when a server
  response omits its own `error` message, and read as protocol-level diagnostics, not
  authored copy. `matchmaking.ts` also isn't wired into any screen yet.
- Single-character glyphs (`‹`/`›`/`»`/`★`) and the `TouchControlsView` weapon-slot
  digit labels (`1`/`2`) — universal, not language-dependent.

## 2026-08-15: weapon/character/material/buff display names — finishing design/09's `nameKey` scaffolding

A player screenshot of the Forge screen showed weapon names (`repeater`, `flamer`, …),
the character name (`skirmisher`), and material short codes (`PHY`/`FIR`/…) rendering as
raw English tokens under `zh`. Investigation found this wasn't a gap to design from
scratch: `design/09-content-data.md` already mandates "no display strings in engine
data," and every relevant content type (`WeaponSpec`, `WeaponBlueprint`, `MaterialDef`,
`RunBuffDef`) already carried a `nameKey: string` field (e.g. `'weapon.repeater.name'`)
for exactly this purpose — it was pure write-only scaffolding, never consumed by any
client code, and none of the 8 locale files had a matching namespace. `SkinDef`
(characters) was the one type design/09 never gave a `nameKey` at all.

**`tName()`, a deliberate second entry point alongside `t()`** (`i18n/index.ts`): `t()`'s
`key: TranslationKey` is a closed compile-time union derived from `en.ts`'s own shape —
exactly right for a fixed set of UI labels, but wrong for an open-ended content catalog
(new weapons keep getting added). `tName(key: string, vars?)` reuses the same
lookup/interpolation machinery but accepts a plain runtime string, with the same
"return the key itself on a miss" fallback `t()`'s internal `lookup()` already had —
`i18n/contentNames.test.ts` walks the REAL catalogs (`WEAPON_SPECS`/`SKIN_DEFS`/
`MATERIAL_DEFS`/`RUN_BUFFS`) and asserts every `nameKey` they carry resolves in every
locale, standing in for the compile-time exhaustiveness `t()` gets for free.

New namespaces added to all 8 locale files: `weapon.<id>.name` (25 entries — the actual
ask), `skin.<id>.name` (3, new — `SkinDef` gained a `nameKey` field), `buff.<id>.name`
(4 — the same bug existed in `EventReactor`'s buff-pickup toast, fixed alongside), and
`material.<element>.name` (5, content mirrors the existing `hud.element.*` full names).
`hud.elementShort.<element>` (5) replaces `Forge.ts`'s old `short()` helper
(`e.slice(0,3).toUpperCase()`) for the compact material-bank/cost-line codes — English
values are unchanged (`PHY`/`FIR`/`ICE`/`LIG`/`POI`), only other locales gained real
short forms. `WeaponBlueprint.nameKey` (`blueprint.<id>`) was deliberately NOT wired up
or given a namespace — every blueprint's id already equals its `weaponId`, so Forge
shows the CRAFTED WEAPON's own translated name for a blueprint row rather than
authoring the identical string twice per locale; the field is left in place as a
documented vestige for a future blueprint whose display name genuinely diverges from
its weapon's.

Fixed call sites: `Forge.ts` (blueprint card name, compare-card headers, `charStats`,
material short codes), `compareCard.ts` (the `type` row, previously a raw `DamageType`
string), `WeaponCard.ts` (HUD weapon name — this also fixed a real cache-invalidation
bug: the redraw-skip cache key was still keyed on `spec.name`, the render-only id, not
`spec.nameKey`, so a nameKey-only change would have silently failed to repaint),
`PlayerCard.ts`/`AllyRow` (local player name card + ally tag — deliberately NOT
`resolveSkin()`'s "unknown id → default character" fallback, since that's right for
gameplay-critical stat resolution but wrong for a display-name echo: an unrecognized
skin id still shows itself raw, not a silently-substituted "Vanguard"),
`EventReactor.ts` (weapon/material/buff pickup toasts).

## 2026-08-15 (follow-up): blueprint unlock-source word

A second look at `Forge.ts` while verifying the display-name pass above found the same
class of bug one namespace over: `forge.lockedSource`'s `{source}` placeholder was fed
the raw `WeaponBlueprint.source` enum value (`'purchase'`/`'event'`) straight from
`@dd/engine`, unresolved — e.g. zh rendered `未解锁（purchase）` instead of
`未解锁（购买）`. `'drop'` was never affected; it already renders through its own
dedicated `forge.lockedFind` string and never reaches `{source}` at all.

Fixed the same way as `RARITY_KEY`/`KIND_KEY`/`ELEMENT_KEY`/`ELEMENT_SHORT_KEY`:
`contentKeys.ts` gained `SOURCE_KEY`, typed `Record<Exclude<BlueprintSource, 'drop'>,
TranslationKey>` (`'drop'` deliberately excluded — see above), and all 8 locale files
gained `hud.source.purchase`/`hud.source.event`. `Forge.ts`'s `lockedSource`
interpolation now reads `t(SOURCE_KEY[bp.source])` instead of the bare enum value.

## Test coverage

`client/src/i18n/i18n.test.ts` — default locale, switching, `{var}` interpolation, an
unknown-placeholder no-op, and a parity check that walks every leaf key in `en.ts` and
asserts every declared locale actually resolves it (guards against the compile-time
`Translations<T>` check ever being weakened or bypassed). 6 tests.

A follow-up pass added: new suites for the four migrated files that had **zero** prior
test coverage — `MainMenu.test.ts`, `PauseMenu.test.ts`, `Settings.test.ts` (including
the language toggle: flips `getLocale()` immediately, relabels itself and the rest of
the screen in the same tap, round-trips `en ⇄ zh`), `EventReactor.test.ts` (toast text
per pickup kind) — plus `settings/store.test.ts` (`locale` migration: a valid saved
locale round-trips, an invalid one — or one missing entirely, i.e. a pre-i18n save —
falls back to `en`, a corrupt save still fails soft). Every already-tested migrated
screen (`Forge`, `HudView`, `LoginScreen`, `PartyScreen`, `Screens`, `RunOutcome`,
`compareCard`) gained a `zh` locale-switch case asserting translated + interpolated

such file resets the shared locale singleton in `afterEach` so a leaked `setLocale`
can't bleed into the next test. 739 client tests total (was 681 at initial ship).

**2026-08-25: every locale is now swept for LAYOUT, not just for text.** The two bugs below
(2026-08-14's `autoWidth` and 2026-08-15's Pixi measure-vs-paint canvas split) were both a
translated label not fitting its own widget, and both were found live rather than by a test —
a locale case that asserts `.text` says nothing about where the glyphs land. When the menus
picked up a fit-scale for short viewports (design/04's Viewport section),
`client/src/game/screens/viewportFit.test.ts` got a locale axis: all nine full-screen screens
laid out in **all eight shipped locales** at the tightest real viewport (844x390), asserting
every widget's bounds stay inside it. That is the first test in this repo that would catch a
de/ru string pushing a screen past its own edges. It is not a substitute for the two fixes
below — it measures with the approximate metrics of `screens/fakeTextCanvas.ts`, since this
environment has no real canvas — but it does bound the failure to "roughly fits".

## 2026-08-03: six more locales, browser-language auto-detect, a CJK word-wrap bug fixed, one plural mismatch reworded

Four follow-ups from this doc's own "Explicitly not built" list, all shipped the same day:

- **Six new locales**: `de`/`fr`/`es`/`pl`/`ru`/`it` (German, French, Spanish, Polish,
  Russian, Italian) join `en`/`zh` — each a full `Translations<typeof en>` translation
  (`client/src/i18n/locales/{de,fr,es,pl,ru,it}.ts`), wired into `index.ts`'s `Locale`
  union/`LOCALES`/`MESSAGES`. `i18n.test.ts`'s existing "locale parity" test (which
  already walked every leaf key in `en.ts` against every declared locale) covers all six
  for free — a missing/untranslated key fails it exactly as it always has for `zh`.
  `Settings.ts`'s language control changes shape accordingly: the old `en`⇄`zh`
  two-entry swap (`OTHER_LOCALE`) doesn't scale to 8, so it's now a `nextLocale()` cycle
  through `LOCALES`' declared order, wrapping at the end — still a single tap-to-cycle
  button, not a picker/list widget (a real list would read better at this size, but
  that's a new widget shape this project doesn't have elsewhere yet; deliberately not
  built here). A third locale was previously listed as "not built, no target language" —
  the target languages were supplied this time, so this is that item done, not a
  reversal of the earlier caution.
- **Browser/system locale auto-detection on first boot**: `index.ts`'s
  `detectBrowserLocale(languages)` (pure, injectable — matches this project's DI
  convention) maps `navigator.languages`/`navigator.language` (base subtag only, so
  `'zh-CN'`/`'zh-Hans'` → `'zh'`) to a supported `Locale`, falling back to
  `DEFAULT_LOCALE` when nothing matches. Wired into `settings/store.ts`'s
  `createWebSettingsStore` — but ONLY when `localStorage.getItem(key)` returns `null`,
  i.e. a genuinely fresh install. A save that predates `locale` entirely (a pre-i18n
  save) or is corrupt still falls back to plain English via `migrate()`, unchanged —
  a RETURNING player's implicit "never touched the language setting" should never be
  silently overridden after the fact just because one field happens to be absent from
  their save. This distinction is the one design decision in this pass; everything else
  is direct translation/mechanical wiring.
- **A real CJK line-wrap bug, found and fixed, not just theorized**: this doc used to
  flag Pixi's own `wordWrap` as untested for CJK content (it only breaks at
  whitespace-delimited "words"; Chinese/Japanese/Korean text has none). Verified live
  under the `zh` locale (real Chrome, not the sandboxed preview pane — see the engine-
  conventions memory) by forcing `PortalPrompt`'s title text to an unbroken long Chinese
  string with no natural break point: it overflowed the panel as one line instead of
  wrapping, confirmed by screenshot. `TextStyle.breakWords = true` (forces a
  character-level break when no earlier break point exists) fixed it — re-verified live,
  now wraps cleanly to multiple lines within the panel. Applied to `PortalPrompt.ts`'s
  `titleText` (the one place this was a live risk — `hud.portalTitle`'s current copy
  happens to be short enough to never hit it, but a future longer translated string
  would have) and, as defense-in-depth, `Forge.ts`'s `infoText` (not currently at risk —
  its content is already length-capped for an unrelated reason, the 2026-08-01 Forge
  overflow fix — but costs nothing to guard the same way). Live browser verification is
  the only check that can prove the ACTUAL wrap behavior: Pixi's text-wrap layout needs
  a live canvas, unavailable in this repo's plain-node vitest (the same constraint the
  font-metrics-clipping bug hit). A follow-up pass added a config-pinning regression
  test to each (`PortalPrompt.test.ts`, `Forge.test.ts`) that asserts
  `wordWrap`/`breakWords` are both `true` on the relevant `Text` style — it can't
  re-verify the wrap pixels themselves, but it does mean a future edit that silently
  drops `breakWords` (e.g. someone "simplifying" the style object) fails a test instead
  of shipping the bug back unnoticed.
- **The `+1 materials banked` singular/plural mismatch reworded**: `results.materialsBanked`
  changed from `'+{count} materials banked'` to `'Materials banked: {count}'` — a
  count-agnostic label style ("Score {score}" and "Time {m}:{ss}" on the same result
  screen already use this shape) that reads correctly at any count without needing
  plural logic. Applied the same way in `zh.ts` (which had no grammatical problem to
  begin with, but matches the new phrasing for consistency) and used from the start in
  all six new locales — several of which (Polish, Russian) have plural rules far more
  complex than English's two-way singular/plural split (1 / 2-4 / 5+ noun forms), so the
  same "label: number" dodge was applied pre-emptively everywhere a count sits next to a
  noun in the new translations (e.g. `forge.moreAvailable`), rather than only fixing the
  one string that happened to be reported. This is NOT a general pluralization engine —
  `{count}`-style templates are still interpolated as-is everywhere else; a future
  string that truly needs grammatical agreement (not just a label) would still need one.

Test totals: 593 client tests (was 582 — 591 for the locales/detection/plural-fix pass,
+2 for the `wordWrap`/`breakWords` config-pinning tests added right after), `tsc
--noEmit` clean (every new locale file type-checks as a `Translations<typeof en>` — a
missing/extra key is a build error, not a runtime gap).

## 2026-08-14: Settings' translated buttons overflowed/mis-centered in longer locales (autoWidth)

A player screenshot showed Russian's Settings screen with `ЯЗЫК: Русский` /
`УПРАВЛЕНИЕ: ЛЕВША` / `ВКЛЮЧИТЬ ЗВУК` reading off-center relative to their neighbors,
and the longest of them visibly overflowing its own button. Root cause: `Settings.ts`'s
four translated buttons (language, control-layout, mute/unmute, back) were built with a
fixed pixel width sized for the English string (`w: 160` for `LANGUAGE: English`, `w:
200` for `CONTROLS: LEFT-HANDED`, etc.) — the shared `ui/widgets.ts` `Button` centers its
label *within* that fixed box (`anchor.set(0.5)`), it never resizes the box to the label.
A translated string longer than the English one it was sized for either overflowed the
box outright, or (for the mute/back pair, positioned via a hardcoded half-width offset
from screen center) threw off the pairing/centering math once one side's real width
diverged from the constant it was never actually measured against.

Fixed in two parts:
- `Button` gained an opt-in `autoWidth` flag (`widgets.ts`): the box now grows to fit the
  *current* label (measured via `estimateMonoWidth`, the same canvas-free monospace
  estimator `StatChip`/`WeaponCard`/`PlayerCard` already use for exactly this class of
  problem — see `ui/textWidth.ts`), with the constructor's `w` becoming a minimum rather
  than a fixed size. Off by default, so the other 50+ `Button` call sites across the app
  keep their exact prior fixed-width look; only Settings' four translated buttons opt in.
- `Settings.ts`'s row layout now centers each button (and the mute+back pair, which keep
  a fixed 20px gap between them) off its *current* `Button.width`, not a value baked in
  for the English string's length — recomputed on every `syncWidgets()` call (a `show()`
  or a locale/mute/control-layout tap), since an `autoWidth` button's width can change
  independently of any actual resize.

`Button.width` is a plain getter backed by the same `estimateMonoWidth` arithmetic
`textWidth.test.ts` already covers — no real canvas needed, so `Settings.test.ts`/
`widgets.test.ts` assert on it directly (formula-matches-width, never-shrinks-below-
minimum, stays-centered-across-a-locale-driven-resize). Confirmed live via claude-in-chrome
against the real dev server: cycling to `ru` now shows both buttons correctly sized/
centered, and toggling to the longer `ВКЛЮЧИТЬ ЗВУК` unmute label grows its box instead of
overflowing while the back button shifts to stay paired with it. Render-only, no
`ENGINE_VERSION` impact.

## 2026-09-10: the same bug on six more screens, and the sweep that finds them

The 2026-08-14 pass above fixed Settings and said so explicitly — *"only Settings' four
translated buttons opt in"*. Nothing checked the other fifty-odd buttons, and a sweep written
in the same spirit as `viewportFit.test.ts` (all eight locales, every screen) found **17
overflowing labels across six screens** the moment it existed:

| screen | button | locales |
| --- | --- | --- |
| MainMenu | ACCOUNT (the greeting) | de, es, fr, it, pl, ru |
| MainMenu | SETTINGS | de, it |
| PartyScreen | CREATE / JOIN / START / LEAVE | de, es, fr, it, pl |
| Forge | CLEAR LOADOUT / START RUN | es, fr, it, ru |
| PauseMenu | QUIT | es |
| LoginScreen | CHANGE PASSWORD | fr |

**`client/src/game/screens/labelFit.test.ts`** is that sweep. Two things had to be true before
it could measure anything real, and both are the reason a bug this visible survived four
months of green suites:

1. **A unit-test button has no icon.** `getUiTexture` answers `undefined` with no art loaded,
   so `Button.setIcon` takes its clear branch and the label CENTRES itself. Shipped, the label
   starts after the chip — a strictly tighter layout. The sweep mocks the texture registry, so
   every screen gets an icon exactly where it already asked for one.
2. **`fakeTextCanvas` charges 0.6em per character.** Measured against the real font, Latin at
   these sizes is ~0.55em (so the estimate errs safe), and CJK is about a full em (so it
   under-measures Chinese). A passing `zh` row is not evidence; a passing Latin row is.

Fixed three ways, and which one applies is a layout question rather than a language one:

- **`autoWidth` where the layout has room.** `PartyScreen`'s five buttons are stacked rows on
  a 760-wide design space, so the box grows and the row re-centres off `Button.width` — the
  same shape Settings adopted in 2026-08-14, now with its own precedent to point at.
- **A shorter word where it does not.** Eleven labels on buttons that sit in fixed pairs or
  bars: `EINSTELLUNGEN`→`OPTIONEN`, `IMPOSTAZIONI`→`OPZIONI`, `CHANGER LE MOT DE PASSE`→
  `CHANGER LE MDP`, `VIDER L'ÉQUIPEMENT`→`VIDER`, and so on. A shorter label is better than a
  clipped one, and this is the cheaper half of the fix by a wide margin.
- **A structural change where the length is not ours at all.** The lobby's account chip
  carried `Hi, {username}` — a greeting plus a **player's name**, so no fixed width can be
  right in any locale. It now carries the bare name, ellipsised past 12 characters, on an
  `autoWidth` box, with the ACCOUNT/SETTINGS pair centred from the measured widths; the
  localised greeting is still shown in full on the portal's label, which has a whole row.

Two widget bugs came out of it, both in `Button` and both invisible while no test gave a
button an icon: **`redraw()` re-centred the label** (undoing `setIcon`'s offset on every
`setFill`/`setBorder`/auto-width `setText`, so the label ran off the right edge), and
**`autoWidth` did not pay for the icon lane** (it sized the box for a centred label, then the
icon pushed the text out of it). `widgets.test.ts` pins both; the mutation that restores the
old `redraw` is caught.

## 2026-08-15: the Russian labels were still outside their buttons — Pixi measures text on a different canvas than it paints on

A direct follow-up to the `autoWidth` section above, from another player screenshot of the
same screen: `ЯЗЫК: Русский` / `УПРАВЛЕНИЕ: ЛЕВША` / `ВКЛЮЧИТЬ ЗВУК` still sat visibly
outside (and to the LEFT of) their button backgrounds, while the Italian screenshot beside
it looked perfect. The mis-centering — not just overflow — is what makes this a different
bug from the one `autoWidth` fixed: the boxes were sized correctly this time.

Root cause is one layer below i18n, in Pixi itself, and is written up in full in
`01-rendering.md`'s "Text measurement" section. In short: Pixi measures text on an
`OffscreenCanvas` but rasterises it on a DOM canvas, and Chrome does not resolve the CSS
generic families (`monospace`, `sans-serif`, …) identically in the two — an OffscreenCanvas
has no document to read the user's configured fixed-width font from. Measured live on
Windows Chrome with `bold 15px monospace`, Cyrillic came out at **8.25px/char painted vs
17px/char measured** (Latin agreed to within 10%), so `Text.width` for the language label
was 205px against 107px of actual glyphs, and `Button`'s `anchor.set(0.5)` dutifully
centred the 205px phantom — pushing the visible text ~49px left of its box.

**Why this bites i18n specifically.** The two fonts Chrome picks agree closely on Latin
and disagree wildly outside it, so every Latin locale (`en`/`de`/`fr`/`es`/`it`/`pl`)
renders correctly and only the non-Latin ones break. That is exactly the shape of bug that
survives review and English/Italian QA, and it is worth assuming any *future* non-Latin
locale (Greek, Hebrew, Thai, Devanagari) would have hit it too — this was never a Russian
problem.

**Fix:** `client/src/render/textMetrics.ts`'s `pinTextMeasurementToPaintCanvas()`, called
first thing in `main.ts` and `main.wechat.ts`, points Pixi's measurement canvas at a
`DOMAdapter.get().createCanvas()` — the exact call `CanvasPool` uses for the paint canvas —
so measure and paint agree by construction, for every font family and every script. It has
to run before the first `Text` exists, since Pixi memoises that canvas on first use.

`Settings.ts`, `widgets.ts` and `textWidth.ts` are unchanged: `estimateMonoWidth`'s 0.6em
assumption was never the problem (the real advance is 0.55em, i.e. the boxes had headroom),
and the 2026-08-14 layout maths above is correct as written.

Test coverage is `client/src/render/textMetrics.test.ts` (12 tests) — see
`01-rendering.md` for how it fakes both canvas kinds with the real measured advances so
"pinned vs. not pinned" is a genuine difference rather than two names for the same stub.
It includes an all-locales sweep asserting every settings label fits inside its box in all
8 locales, which is the piece that would have caught this class of bug from a Latin-only
