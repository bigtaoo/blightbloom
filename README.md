# Blightbloom

**Blightbloom** /《绽晶》 (Chinese title 暂定 — see `design/13`'s *Shipping title*). Renamed from
the codename *DayDayUp* on 2026-09-06. The `daydayup` string survives on purpose in three
places, and none of them is a leftover: persisted keys (`daydayup.*` in localStorage,
`daydayup.replay` in a saved replay, `server/data/daydayup.db`), the deployed Cloudflare
Worker names, and the `de.elk.daydayup` bundle id. Renaming any of those is a migration.

A 2D top-down (3/4 view) free-shooter roguelite, inspired by Soul Knight. The core of the game is a **rich weapon system** — ranged and melee, where melee weapons can block and deflect bullets. Characters are a **flat roster of balanced side-grades**, not skins: each carries its own `(maxHp, maxShield, maxEnergy)` triple plus one shield-break passive, with its theme confined to the orb-core and never to the weapons (`design/13`).

## Structure

An npm workspace. Every package is consumed as TypeScript **source** — there is no
build step between them, so a shared type can never go stale against a built artifact.

| Directory | Contents |
|-----------|----------|
| `design/` | Design and technical decisions (architecture, data models, rationale) |
| `art/` | Art assets and asset conventions |
| `engine/` | `@dd/engine` — the deterministic simulation core (`design/06`, `design/08`). Renderer- and host-free: it compiles without the DOM lib and may not import any other package. Consumed by client, server and both tools. See `engine/README.md`. |
| `client/` | Game client. Single-engine PixiJS v8. Targets: Web / PC / Android / iOS / WeChat mini-game / game portals (`design/20`). See `client/README.md`. |
| `server/` | Backend: the frame-broadcast **gameserver** (WebSocket data plane), the **matchsvc** matchmaking/ticket control plane, the **billsvc** billing plane, and a **backup** worker that snapshots both SQLite files daily. See `server/README.md`. |
| `tools/` | Authoring tools, none of them shipped to players. `animator` — the `.tao` rig/clip editor (`design/12`); its `projects/*.editortao` files are the authoring source for every rig in the game. `map-editor` — arena/room authoring, the authority on the `ArenaMap` layout the engine only consumes (`design/15`). `png-pipeline` — a dependency-free pure-Node PNG codec (`pngCodec.mjs`) plus the `compress.mjs` trim/downsample/re-encode step every asset in `client/public/` went through. `desktop-shell` — an Electron app hosting `animator` and `map-editor` as switchable pages in one window, with a native file I/O bridge (`window.nwDesktop.fs`) so Save/Load use real OS dialogs instead of the browser File System Access API. |
| `world/` | Authored world data in JSON form — today only `dungeons/`, the PvE level-1 room library and floor maps the map editor round-trips. PvP's launch map is TypeScript content instead: `engine/world/arenas/` (`arena_launch`, "The Seven Districts") |

`tsconfig.base.json` and `build/ddAlias.mjs` are the type-side and bundler-side halves
of one `@dd/*` path map — kept as a single file each so they cannot drift apart.

## Tech stack (summary)

- **Single engine: PixiJS v8** (UI included). No Three.js — the game is 2D top-down; the 3D feel is faked with Y-sorting, height/shadow separation, and a tilted view.
- **Fully open source (MIT)** so any issue can be patched or forked. This is the key trade-off versus closed-editor engines like Cocos Creator.
- **WeChat mini-game is the most constrained target** (no DOM, no `fetch`, no WebGPU → WebGL fallback, base-library version must be verified on a real device). It does *not* use `weapp-adapter` — the bundle installs Pixi's own `DOMAdapter`. As of 2026-08-25 real art loads there and the game boots, renders, is tappable, is navigable end to end, enters the map and shows readable text in the real simulator (verified: `Game.start()` runs, the render loop produces real on-screen content, a real PLAY-button tap drives a real screen transition, the menus FIT the 844x390 landscape-phone viewport instead of overflowing it, room building no longer throws on a canvas Pixi cannot identify, and labels rasterise instead of coming out blank) — and the five custom shaders are confirmed to COMPILE and do real work there, measured one pass at a time against a live room rather than inferred from "the frame is non-blank". Real-device verification (frame rate, touch feel, lowest base-library version) is what remains, and it now has something to act on: `render/quality.ts` adds `auto`/`high`/`medium`/`low` render tiers — `low` turns off all four full-viewport filter passes and halves the renderer resolution (render-target switches 11 → 1), `medium` keeps the one lighting pass and drops the three above it (framebuffer binds 11 → 3) — with an `auto` watchdog that steps a device down a rung when it cannot hold the frame, so a handset reports itself in the settings screen as `AUTO (MEDIUM)` / `AUTO (LOW)`. Separately, and for battery rather than for framerate (a live report of heavy drain on a phone and an iPad, 2026-09-08): `game/powerBudget.ts` stops drawing the world layer outside a run — every menu, pause and result screen is backed by opaque full-viewport art, so a finished run's room was being rendered invisibly at the display's refresh rate — and caps the render rate at 60 in a run (30 if the player picks it) and 30 elsewhere, where before there was no cap and a 120 Hz panel drew four frames per 30 Hz sim tick. **This target is on the network as of 2026-09-09** (`design/21` §9): the runtime still has no `fetch` and no `localStorage`, so `platform/wechat/weChatFetch.ts` wraps `wx.request` and `weChatStorage.ts` wraps `wx.getStorageSync` — which is what let analytics be installed here at all (the install id now persists instead of being minted per visit, so DAU counts installs rather than visits) and what makes the feature-flag poll deliver instead of sitting inert. Two things still need a handset, both silent when wrong: the build must be made with `VITE_MATCHSVC_URL=https://…` (a plain `npm run build:wechat` bakes in localhost, which `wx.request` refuses) and that host must be in the account's 服务器域名 whitelist. See `design/04-wechat.md`'s **On-device test plan** and `design/01-rendering.md`'s **power budget**.

See [design/](design/) for the full record.

## Getting started

Install once at the repo root — it is a workspace, so this covers every package.

```bash
npm install
```

```bash
npm run dev        # client dev server, http://localhost:5173
```

| Command | What it does |
|---------|--------------|
| `npm run check` | Typecheck **and** test every package — the one command to run before committing |
| `npm run coverage` | Measure every package under v8, print the report, then run the **90% line / 90% branch** gate. Not part of `check` (it is minutes, not seconds) — CI runs it as its own job on every push and PR |
| `npm run check:logic` | The 12 named logic-consistency gates (golden hash, version contract, determinism lint, step order, smoke, the parity sweeps). They also run inside `npm test`; this runs them BY NAME, and fails closed if one has been renamed away |
| `npm test` | Test every package |
| `npm run typecheck` | `tsc --noEmit` in every package |
| `npm run dev:server` / `npm run dev:matchsvc` | Co-op gameserver / matchmaking service |
| `npm run dev:animator` / `npm run dev:map-editor` | The two authoring tools |
| `npm run dev:desktop-shell` | The Electron shell hosting both authoring tools (run the two `dev:` commands above first, in separate terminals) |
| `npm run test:pvp-sim` | The offline PvP balance harness (`client/sim/`, kept out of the default test glob — ~6s) |
| `npm run test:pve-sim` | The PvE level simulator — bot-driven real runs of level 1, per-room reaction window / peak shooters / clear rate and the difficulty gates, plus both halves of the loot economy: what a floor HANDS YOU (weapons / potions / materials / energy per floor) and what a floor COSTS to clear (trigger pulls, projectiles, melee share) (`client/sim/`, also out of the default glob) |
| `npm run test:weapon-sim` | The per-weapon sweep — every player-facing weapon plays the shipped level over 8 seeds, reporting kills / ticks-per-kill / damage taken / depth, and gating that no weapon is inert (`client/sim/`, also out of the default glob — ~10s) |
| `DD_REPLAY=<path> npm run replay:inspect` | Read one recorded run (a `ddreplay-*.json` a player saved with the HUD's ● button or F9) and report every drop's closest approach, swept path, gate and `pickup` event (`client/sim/replay/`) |

### Branching

`main` is push-protected and only advances through a merged pull request — the repository
ruleset "Only PR" requires one, and requires the four `check.yml` jobs (`logic consistency`,
`check`, `coverage`, `sims`) to be green and the branch to be up to date first. Work lands
on a daily integration branch named `DD.MM.YYYY`, which is what opens that PR; task-sized
work gets its own worktree and `feat/<slug>` branch off the day's branch. Full rules, and
the commands, in [`CLAUDE.md`](CLAUDE.md#branches-the-daily-branch-and-pull-requests).

## Deployment

The client is live at **https://b.gamestao.com** — static assets (`client/dist`) served
by a Cloudflare Worker (`daydayup-client`, `wrangler/client.jsonc`), same Cloudflare
account as the `funny` project's `gamestao.com` zone. The same deploy hosts the game's
**privacy policy and terms** (`/privacy`, `/terms` — `client/public/*.html`), which a game
portal requires and the in-game data notice links to.

`.github/workflows/client-deploy.yml` auto-deploys on every push to `main` that touches
`client/**` or `engine/**` (the client build reads the engine as source via the vite
alias), or via manual `workflow_dispatch`. Gated behind repo variable
`CLIENT_DEPLOY_ENABLED` and repo secrets `CLOUDFLARE_API_TOKEN` /
`CLOUDFLARE_ACCOUNT_ID`.

Manual deploy (fallback, or first-time setup):

```bash
npm run build -w client
npx wrangler deploy -c wrangler/client.jsonc
```

An already-open tab picks up a deploy on its own. The client build emits
`dist/version.json` (`build/versionManifestPlugin.mjs` — a hash over the bundle *and*
`client/public/`, so an art-only deploy counts too), and
`client/src/platform/web/autoReload.ts` re-checks it whenever the player returns to the tab,
reloading when it no longer matches the hash the page booted with — held back while a run or
an online session is live, then applied on the next return. `client/public/_headers` keeps
`index.html`/`version.json` uncached at the edge, which is what makes the check meaningful;
don't drop it. Production builds only — the dev server keeps using Vite HMR. Ported from
`funny`'s equivalent; see `design/ROADMAP.md`'s 2026-08-15 entry for how the two differ.

### Game portals (CrazyGames)

A fourth target, and the first one that constrains what the client may DO rather than what it
CAN do — see [design/20-game-portals.md](design/20-game-portals.md).

```bash
npm run build:crazygames -w client   # → client/dist-crazygames/ — zip this and upload it
```

It is the same game: same `WebPlatform`, same renderer, nothing under `client/src/game/`
knows the portal exists. What differs is a third entry point
(`client/src/main.crazygames.ts`), relative asset paths (`base: './'` plus
`baseAssetHost`, because the portal serves the bundle from a path of its choosing), the SDK
integration in `client/src/platform/crazygames/` (loading/gameplay brackets, a between-runs
midgame ad, a menu-only banner, mute-and-freeze for the duration of an ad, and one rewarded-ad
offer — double a successful extraction's materials, never a bought-back wipe), one click from
the front door into a run, and no store entry at all — in-game purchases there are invite-only
through the platform's own payment account. Matchmaking defaults to `https://bb.gamestao.com`
in that config, since an uploaded bundle has no localhost to reach.

Two more things differ since 2026-09-08, and both are policy rather than capability. **There is
no login screen there**: that platform disallows a game's own credential login and requires that
a logged-in portal user be signed in automatically, so `LoginScreen` is unreachable on that host
and `platform/crazygames/portalAuth.ts` exchanges the SDK's user token for one of our sessions
from the entry point — a guest is a normal outcome and plays exactly as before. **And the portal
is told about the squad**: a party is announced as a joinable room, the platform's own invite
button carries the join code, an accepted invite lands the player in that party, and other
players' CrazyGames usernames are shown in-match. The account decision behind it — one human on
two platforms is deliberately two accounts — is in design/20.

`__portal.diagnostics()` in the browser console reports the SDK environment, the adblock probe,
whether the gameplay brackets are firing, the account state and the room state. It is the only
instrument for the half of that integration this repository cannot test — **four** of its
findings contradicted the SDK's own documentation, and they are recorded in design/20. The
fourth is why the build loads `crazygames-sdk-v3.js`: the shipped v2 script has no `updateRoom`,
no `leftRoom` and no `isInstantMultiplayer` at all, so the platform's room requirement was
unmet with nothing turning red.

Its account clause has **five** states since 2026-09-08, and the fifth is the instrument being
fixed rather than the integration: a `getUser` that threw used to report as `guest`, because
`settle()`'s whole contract is that a failure is indistinguishable from a call that returned
nothing. That made the likeliest failure of the entire silent-login path — the platform's SDK
logs that `getUser` is still in BETA — look identical to a page of players who are not signed
in. It now reads `getUser BROKEN (<reason>)`, and nothing branches on it: every failure path
still ends at a fully playable guest.

The two authoring tools have the same setup — `wrangler/animator.jsonc` /
`wrangler/map-editor.jsonc` + `.github/workflows/animator-deploy.yml` /
`map-editor-deploy.yml`, gated behind `ANIMATOR_DEPLOY_ENABLED` /
`MAP_EDITOR_DEPLOY_ENABLED` — but those repo variables are **not yet set**, so neither
workflow deploys until that's turned on. Once live they'd serve at
`dd-animator.gamestao.com` / `dd-map.gamestao.com`, which is what the desktop shell's
`tools/desktop-shell/src/tools.ts` `prodUrl` fields point to for a packaged install.

The backend (`gameserver`/`matchsvc`/`billsvc`, design/19) is live at
**https://bb.gamestao.com**, and the client above points at it by default
(`VITE_MATCHSVC_URL`, injected from repo variable `MATCHSVC_URL`). It runs as **nine**
Docker containers on a VPS borrowed from another project (not Cloudflare — a WebSocket
frame relay needs a real process, which Workers cannot host), behind a shared Caddy
instance doing automatic Let's Encrypt: the three planes, a backup worker, the read-only
ops console at **`/admin/`** (`adminsvc`, design/21 — deployed 2026-09-09), and four
off-the-shelf observability images (Loki/Alloy/Prometheus/Grafana, design/19 §10) with
Grafana at **`/grafana/`**. Both consoles are login pages on the public internet, so
compose refuses to start *any* service without their passwords in the untracked `.env`.
The count is spelled out here because it has been wrong three times: the deployed set grows
by service, and this paragraph is the first thing anybody reads. `.github/workflows/server-deploy.yml` +
`server/deploy/ci-deploy.sh` auto-deploy on push to `main` touching
`server/**`/`engine/**`/`client/src/**`, over an SSH key that is forced-command-restricted
on the far end to running exactly that one script — full runbook, including why the
build has to happen locally first (`server/scripts/build.mjs` esbuild-bundles each
entrypoint, resolving the `@dd/engine`/`@dd/game`/`@dd/net` workspace aliases this server
uses so the VPS needs nothing but Docker), in `server/deploy/README.md`. `billsvc` runs in
dev-stub mode — no real Paddle credential exists yet, so the store proxy is proven end to
end but nothing can actually be bought.

The circle that fix landed on was itself wrong, and stood until 2026-08-27: *"a sphere's silhouette is a circle from every angle"* is true of a real camera, and this renderer is not one — it draws the world grid unsquashed while extruding wall heights 1:1 upward in px, i.e. the shear `(x, y, z) -> (x, y - z)`, under which a sphere projects to an ellipse with semi-axes 1 and sqrt(2). The shell is 1.30 taller than wide now, and the two constants are the two halves of how round things read here: squashed = lying on the ground, taller = standing in the world. A third pass on 2026-08-19 stopped looking and started MEASURING the frame (`renderer.extract` at zoom 1, sampled per wall entity from the renderer's own geometry), which found what two look-driven passes had missed: a wall cap raised 104 px read DARKER (44) than the floor it stands on (53), so every other height cue was arguing against the most basic one and losing; each room boundary was drawn as two independent blocks because adjacent rooms each author their own wall, putting a lit/dark seam down the middle of one stone mass; the camera clamp had silently cancelled the wall-height frame extension since the day it shipped, so a room's tallest wall never showed its top; the per-wall stone-relief filter cost 10-32 render targets per room for a measured 0.06% difference and is now off; and both the sphere shading and every ground shadow were sized against a rig's DECLARED body radius while the shipped art paints only 0.68-1.00 of it — which had been painting a hard-edged dark disc onto the background around every crystal enemy, recorded in an earlier session as an over-large shadow. Fixed with an additive cap key light, run merging, a per-room floor light pool (the cheap static half of design/01's parked lightmap), and art-derived body radii guarded by a test that re-decodes the real PNGs every run. One wall then took four more reports on 2026-08-19, all of them the same defect: every tonal constant had been measured on an EAST-WEST wall, where the cap is a thin band under a lit coping, and applied unchanged to a north-south run, where the cap is 100% of what you see. The flat additive key light was destroying the swatch's contrast RATIO (2:1 to 1.4:1) and is now the cap drawn a second time in `add` mode; caps tile in world space so an L corner's two blocks share one stone field; the east band no longer paints a grey stripe down a run's whole top; and a deep run now TUCKS under the wall it meets, stopping just below that wall's crown course — the longest unbroken horizontal in a room, and the line the eye identifies a back wall by. The crown line is measured per element, because `wallface_ice.png`'s coping band is a third shorter than fire's — a bug found by the new `client/src/game/scene/wallComposition.test.ts`, which runs the real level-1 floors through the real wall pipeline and decodes every shipped face swatch to check the constant against its art. **The art-direction blanks are closed as of 2026-08-25**, all three of them locked design rules that had shipped half-built rather than optional extras: design/13's element colour-plus-icon pair is a *dual-channel* rule and only the colour channel had ever existed, so the five icon glyphs (flame/snowflake/bolt/skull/gem) now ride on elemental mobs, on each active status aura, in the HUD's damage badge and on a dropped weapon — vectors, not art, and drawn as solid masses because a stroke is invisible at the 3-8 px these render at; the poison biome got its three swatches, so every element in the closed five has real stone (its brief carries a gameplay clause the others do not — a green floor makes poison bullets and poison-tinted mobs camouflage, so "dial the green down" is stated numerically in the prompt and asserted on the shipped pixels); and weapon rarity's overlay spec is locked as **count, not hue** — four of the five rarity hues turned out to already sit on a reserved element hue and `common` white is byte-identical to physical's neutral, so no palette could have separated them, whereas a countable 0-4 marks cannot be confused with a hue at all
